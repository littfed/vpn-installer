## 1. Введение и Executive Summary

При проектировании надежного инструмента развертывания VPN/прокси (`vpn-installer`) ключевой задачей является не только устойчивость к блокировкам DPI (ТСПУ в РФ), но и **гарантия абсолютной конфиденциальности пользователя**. 

Шифрование туннеля само по себе не защищает пользователя от деанонимизации. Современный веб-стек насыщен протоколами, механизмами оптимизации и системными API, которые способны раскрыть реальный IP-адрес клиента, его географическое положение и интернет-провайдера (ISP) даже при активном защищенном соединении.

### Ключевые векторы риска для клиента VPN

```
+-----------------------------------------------------------------------------------+
|                                 КЛИЕНТСКИЙ ХОСТ                                   |
|                                                                                   |
|  [ Браузер: WebRTC ] ----(STUN UDP:3478 мимо прокси)----> [ Реальный IP утекает ] |
|  [ Браузер: JS API ] ----(Intl.DateTime / Languages)---> [ Timezone Mismatch ]   |
|  [ OS Stub Resolver ] ---(Windows SMHNR / Fallback)-----> [ DNS Leak к ISP ]     |
|  [ Dual-Stack Стек ] ----(IPv6 AAAA via Happy Eyeballs)-> [ IPv6 Leak мимо туннеля|
|  [ TCP/IP Стек ] --------(MSS:1380, TTL:128 vs Linux)--> [ OS Fingerprint Mismatch|
+-----------------------------------------------------------------------------------+
```

1. **DNS Leaks:** ОС отправляет DNS-запросы через домашнего провайдера из-за механизмов Smart Multi-Homed Name Resolution в Windows или отсутствия принудительного перехвата порта 53.
2. **WebRTC IP Leaks:** Браузер выполняет ICE candidate gathering, отправляя прямые UDP-пакеты к публичным STUN-серверам в обход L4-прокси (SOCKS5/HTTP) и выдавая реальный публичный IP (`srflx candidate`).
3. **IPv6 Leaks:** Домашний провайдер выдает нативный IPv6, а VPN-сервер работает только по IPv4. В результате весь IPv6-трафик идет в открытом виде мимо туннеля из-за приоритета IPv6 в RFC 8305 (Happy Eyeballs).
4. **TCP/IP Fingerprinting (p0f):** Несоответствие между операционной системой клиента (например, Windows 11) и TCP-параметрами выходного узла (Linux VPS), а также специфический MTU/MSS туннелей (1280–1420 вместо стандартных 1500).
5. **Антифрод и IP Reputation:** Хостинговые ASN (Hetzner, DigitalOcean, OVH) имеют высокий Fraud Score, что приводит к блокировке банков, маркетплейсов и AI-сервисов (OpenAI, Claude).

Ниже представлен детальный технический анализ каждого вектора, инструментарий аудита и инженерные решения для ядра `sing-box` в составе `vpn-installer`.

## 2. Механизмы и векторы утечек реального IP и местоположения

### 2.1. DNS Leaks: архитектура атак и методы деанонимизации

DNS Leak (утечка DNS) — это ситуация, при которой сетевой трафик пользователя направляется через VPN-туннель, однако запросы на разрешение доменных имен (DNS) отправляются на DNS-серверы локального интернет-провайдера (ISP) или сторонние открытые резолверы в открытом незашифрованном виде.

#### 2.1.1. Принцип работы тестов DNS-утечек (UUID-поддомены и Authoritative NS)

Сервисы проверки утечек DNS (например, BrowserLeaks, IPLeak.net, dnsleaktest.com) используют механизм делегирования зон DNS для однозначной идентификации источника запроса:

```
+----------+      1. Resolve <uuid>.leak-test.com      +------------------+
| Клиент   | ----------------------------------------> | Системный        |
| (Браузер)|                                           | DNS-резолвер     |
+----------+                                           +------------------+
     |                                                          |
     |                                                          | 2. Рекурсивный запрос
     |                                                          v
     |                                                 +------------------+
     |                                                 | Upstream DNS     |
     |                                                 | провайдера (ISP) |
     |                                                 +------------------+
     |                                                          |
     |                                                          | 3. Запрос NS
     |                                                          v
     |                                                 +------------------+
     | 4. WebSocket / HTTP polling:                    | Authoritative NS |
     |    "Какие IP резолвили <uuid>?"                 | (leak-test.com)  |
     | <---------------------------------------------- | Фиксирует IP     |
     |                                                 | upstream-сервера |
     +-------------------------------------------------+------------------+
```

1. **Генерация уникального токена:** Клиентский JavaScript генерирует криптографически стойкий уникальный идентификатор сессии (UUIDv4 или случайную шестнадцатеричную строку длиной 16–32 байта).
2. **Формирование серии запросов:** Формируется серия доменных имен вида:
   `a1b2c3d4e5f6-01.leak-test.example.com`, `a1b2c3d4e5f6-02.leak-test.example.com`, ..., `a1b2c3d4e5f6-10.leak-test.example.com`.
3. **Инициация резолва:** Клиент инициирует загрузку некэшируемых микро-ресурсов (через `fetch()`, `<img>` или `new Image().src`) по этим доменам. Так как поддомен уникален, он гарантированно отсутствует в DNS-кэше браузера и локального резолвера.
4. **Рекурсивная цепочка:** Локальный резолвер обращается к вышестоящему DNS (upstream), который в конечном итоге обращается к Authoritative Name Server (NS) тестовой платформы, обслуживающему зону `leak-test.example.com`.
5. **Логирование на стороне NS:** Авторитетный сервер фиксирует:
   - IP-адрес входящего запроса (это IP-адрес рекурсивного резолвера, выполнившего запрос к NS);
   - Точное имя запрошенного поддомена (из которого извлекается UUID сессии);
   - Временную метку (timestamp).
6. **Сопоставление результатов:** Клиент через защищенный канал (HTTPS/WebSocket) опрашивает API тестового сервиса: `/api/dnsleak/results?session=a1b2c3d4e5f6`. Сервер возвращает список всех IP-адресов, запросивших домены с данным UUID.
7. **Вердикт:**
   - Если все зафиксированные IP принадлежат резолверам VPN-сервера или доверенным анонимным DoH-серверам — **Утечек нет**.
   - Если среди IP обнаружен адрес, принадлежащий автономной системе (ASN) домашнего интернет-провайдера пользователя — **Зафиксирован критический DNS Leak**.

#### 2.1.2. Причины утечек: Fallback, Windows SMHNR, Linux systemd-resolved

Существуют три основные архитектурные причины возникновения утечек:

##### 1. Windows Smart Multi-Homed Name Resolution (SMHNR)
Начиная с Windows 8 и во всех версиях Windows 10/11 по умолчанию активна служба оптимизации разрешения имен.
* **Механика:** При наличии нескольких активных сетевых адаптеров (например, физический Ethernet/Wi-Fi и виртуальный Wintun-интерфейс VPN) DNS-клиент Windows отправляет DNS-запросы **параллельно на все сетевые интерфейсы**.
* **Утечка:** Первый ответивший сервер признается валидным. Локальный провайдерский DNS обычно отвечает за 2–5 мс, в то время как DNS через VPN отвечает за 40–80 мс. В результате:
  1. Провайдер видит 100% запросов пользователя.
  2. В ответе провайдера могут содержаться поддельные IP (DNS Spoofing / блокировки РКН).
* **Отключение:** Требуется установка флага групповой политики:
  `HKLM\Software\Policies\Microsoft\Windows NT\DNSClient\DisableSmartNameResolution = 1` (DWORD).

##### 2. Fallback на системный резолвер при таймауте
Если в конфигурации клиента указан удаленный DNS-сервер (например, `10.0.0.1` внутри туннеля), но на линии происходит потеря UDP-пакетов или задержка превышает 1.5–2 секунды, сетевой стек ОС производит автоматический откат (fallback) на резервные DNS-серверы, настроенные на физическом адаптере (DHCP от роутера).

##### 3. Особенности `systemd-resolved` в Linux
В современных дистрибутивах (Ubuntu, Debian, Fedora) `systemd-resolved` использует логику маршрутизации запросов на основе доменов ("routing domains"). Если VPN-интерфейс не зарегистрировал домен маршрутизации `~.` (глобальный wildcard), `systemd-resolved` отправляет запросы по принципу round-robin между физическим интерфейсом и VPN.

### 2.2. WebRTC IP Leaks: сбор кандидатов ICE в обход туннеля

WebRTC (Web Real-Time Communication) — стандарт W3C/IETF, обеспечивающий прямое P2P-взаимодействие (аудио, видео, передача данных) между браузерами без промежуточных медиа-серверов.

#### 2.2.1. Спецификация WebRTC ICE (RFC 8445), STUN (RFC 8489) и TURN (RFC 8656)

Для установления прямого соединения между двумя пирами, находящимися за NAT и фаерволами, WebRTC использует протокол **ICE (Interactive Connectivity Establishment)**:

```
[ Браузер ] ---(1. STUN Binding Request, UDP:3478)---> [ Публичный STUN-сервер ]
            <---(2. STUN Binding Success Response)----
                 XOR-MAPPED-ADDRESS: 95.24.xx.yy (Реальный IP клиента)
```

1. Клиент формирует предложение соединения (SDP Offer) через `RTCPeerConnection`.
2. Браузер запускает процесс **ICE Candidate Gathering** (сбор кандидатов на соединение).
3. Для преодоления NAT браузер обращается к STUN-серверам (порт 3478 UDP), отправляя `Binding Request`.
4. STUN-сервер возвращает атрибут `XOR-MAPPED-ADDRESS`, содержащий публичный IP и порт, с которого фактически пришел UDP-пакет.

#### 2.2.2. Классификация кандидатов: `host`, `srflx` и `relay`

В терминологии RFC 8445 кандидаты делятся на три категории:

| Тип кандидата | Название | Описание | Уровень риска |
| :--- | :--- | :--- | :--- |
| **`host`** | Host Candidate | Локальный IP-адрес интерфейса (192.168.1.15, 10.0.0.2 или Link-Local IPv6). Получается локально через ОС. | **Средний:** раскрывает топологию локальной сети и схему адресации. |
| **`srflx`** | Server Reflexive | Внешний IP-адрес клиента, определенный STUN-сервером. | **Критический:** раскрывает реальный публичный IP-адрес провайдера в обход VPN! |
| **`relay`** | Relayed Candidate | IP-адрес промежуточного TURN-сервера. Трафик гарантированно идет через сервер. | **Нулевой:** реальный IP скрыт за TURN-релеем. |

Пример кандидата `srflx` в сыром SDP-пакете:
```text
candidate:842163049 1 udp 1686052607 95.24.180.12 58342 typ srflx raddr 192.168.1.45 rport 58342 generation 0
```
Здесь `95.24.180.12` — реальный публичный IP абонента, предоставленный домашним провайдером.

#### 2.2.3. Почему L4-прокси (SOCKS5/HTTP) бессильны перед WebRTC

Большинство пользователей ошибочно полагают, что настройка прокси в браузере (через настройки ОС или расширения вроде FoxyProxy, SwitchyOmega) защищает их от утечек:
* Браузерные прокси-настройки распространяются **исключительно на прикладной HTTP/HTTPS/WebSocket-трафик**.
* Реализация WebRTC в движках Chromium (Chrome, Edge, Brave, Opera) и Gecko (Firefox) при создании медиа-сокетов по умолчанию создает **сырые UDP-сокеты на уровне ОС**, игнорируя системный HTTP/SOCKS5 прокси.
* Пакет STUN Binding Request идет напрямую через шлюз по умолчанию (Default Gateway) физического сетевого интерфейса. Веб-страница с 5 строками JavaScript мгновенно получает реальный IP.

#### 2.2.4. Методы нейтрализации

1. **На уровне браузера:**
   - **Firefox:** в `about:config` установить `media.peerconnection.enabled = false`. Это полностью отключает WebRTC API.
   - **Chromium:** настройка политики `WebRTC IP Handling Policy`:
     - `default_public_interface_only` — использовать только интерфейс с маршрутом по умолчанию.
     - `disable_non_proxied_udp` — полностью запретить UDP-трафик мимо прокси.
2. **На уровне сетевого ядра Sing-box (L3 TUN):**
   - Перехват всего UDP-трафика операционной системы через виртуальный Wintun/TUN интерфейс (`auto_route: true`, `strict_route: true`).
   - Блокировка или проксирование STUN-трафика:
     - Блокировка портов STUN: порт 3478, 5349 (UDP/TCP).
     - Сниффинг протокола: `sniff: true` -> детектирование сигнатур `stun` -> маршрутизация на `block` или `proxy`.

### 2.3. IPv6 Dual-Stack Leaks: тихий обход IPv4-туннеля

#### 2.3.1. Механика утечки в сетях Dual-Stack и алгоритм Happy Eyeballs (RFC 8305)

Подавляющее большинство современных мобильных сетей (LTE/5G) и прогрессивных фиксированных провайдеров работают по схеме **Dual-Stack (IPv4 + IPv6)**: абонент получает серый IPv4 (за CGNAT) и глобально маршрутизируемый публичный префикс IPv6 (обычно `/64`).

Большинство недорогих или стандартно развернутых VPN-серверов настраиваются только с IPv4-адресом (`0.0.0.0/0`).

```
                              [ Клиентский браузер ]
                                   |         |
      (Запрос к google.com)        |         | (Запрос к google.com)
      IPv4 A-запись                |         | IPv6 AAAA-запись
            v                      |         |      v
     [ VPN TUN IPv4 ]              |         | [ Физический адаптер IPv6 ]
            |                      |         |      |
            v                      |         |      v
  [ VPN VPS Сервер ]               |         | [ Домашний ISP IPv6 ]
            |                      |         |      |
            +------------> [ Ресурс назначения ] <---+
                           Сервер видит IPv6 домашнего провайдера!
```

* **Алгоритм Happy Eyeballs v2 (RFC 8305):** Современные браузеры и ОС отправляют параллельные DNS-запросы на получение `A` (IPv4) и `AAAA` (IPv6) записей.
* Если домен имеет AAAA-запись, клиент начинает установку TCP/TLS соединения по IPv6 с преимуществом в 50–250 мс перед IPv4.
* Если в конфигурации VPN-клиента маршрут по умолчанию для IPv6 (`::/0`) не перехвачен виртуальным адаптером, операционная система отправляет IPv6-пакеты **напрямую через физический шлюз домашнего провайдера**.
* **Результат:** Любой сайт с поддержкой IPv6 (Google, YouTube, Cloudflare, Wikipedia, Facebook) фиксирует реальный домашний IPv6-адрес пользователя.

#### 2.3.2. Стратегии решения

1. **Стратегия А: Полноценный Dual-Stack VPN-туннель**
   - Назначение IPv6-адреса на виртуальный TUN-интерфейс (`fdfe:dcba:9876::1/126`).
   - Наличие публичного IPv6 на выходном сервере и перенаправление префикса `::/0` в туннель.
2. **Стратегия Б: L3 Blackholing и DNS-фильтрация (для IPv4-only серверов)**
   - Если сервер не имеет IPv6-связности, IPv6 на клиенте должен быть **жестко заблокирован**:
     - В `sing-box`: параметр `inet6_address: []` или перехват `::/0` с отправкой на `block`.
     - На уровне DNS: флаг `strategy: "ipv4_only"` — sing-box отбрасывает или не запрашивает AAAA-записи, возвращая только IPv4 A-записи.
     - Фильтрация пакетов: отбрасывание всех исходящих IPv6-пакетов через пакетный фильтр туннеля.

### 2.4. Пассивный фингерпринтинг сетевого стека (TCP/IP OS Fingerprinting / p0f)

Пассивный анализ характеристик TCP/IP пакетов позволяет серверу определить операционную систему, версию ядра и наличие промежуточных туннелей без активного сканирования. Инструмент **p0f v3** (автор Michal Zalewski) является де-факто стандартом этого метода.

#### 2.4.1. Анализ MTU/MSS и сигнатур фрагментации

* Стандартный MTU для сетей Ethernet равен **1500 байт**. Соответственно, максимальный размер сегмента TCP (MSS) составляет:
  $$\text{MSS} = \text{MTU} - 20\,(\text{IPv4 Header}) - 20\,(\text{TCP Header}) = 1460\,\text{байт}$$
* Любой туннель добавляет собственные заголовки инкапсуляции и шифрования:
  - **WireGuard / AmneziaWG:** заголовок 60–80 байт -> MTU 1420 -> **MSS 1380 байт**.
  - **OpenVPN (UDP):** MTU 1500 (с фрагментацией) или MTU 1400 -> **MSS 1360 байт**.
  - **VLESS Reality / TCP:** MSS сервера часто зажимается до 1280–1440 байт.
  - **PPTP / L2TP / IPsec:** MTU 1400–1440 байт.
* **Признак утечки/детекции:** Если сервер назначения видит входящий TCP SYN-пакет с `MSS = 1380` или `MSS = 1360`, он с вероятностью >95% определяет наличие туннелирования (VPN).

#### 2.4.2. TCP Window Size, TCP Options и разница TTL/Hop Count

Входящий TCP SYN-пакет несет в себе специфический отпечаток сетевого стека ОС:

| Параметр стека | Linux (ядро 5.x / 6.x) | Windows 10 / 11 | macOS / iOS |
| :--- | :--- | :--- | :--- |
| **Initial TTL** | 64 | 128 | 64 |
| **Window Size** | Динамический (обычно 64240 или кратен MSS: $10 \times \text{MSS} = 14600$) | Фиксированный (обычно 64240 или 65535) | 65535 |
| **Window Scale** | Обычно 7 | 8 | 6 |
| **TCP Options Order** | `MSS, SACK, TS, NOP, WScale` | `MSS, NOP, WScale, NOP, NOP, SACK` | `MSS, NOP, WScale, NOP, NOP, TS, SACK, EOL` |
| **DF (Don't Fragment)** | Всегда 1 | Всегда 1 | Всегда 1 |

#### 2.4.3. Несоответствие User-Agent и сетевого стека при L4-проксировании

Когда пользователь на Windows использует прокси (SOCKS5/VLESS без TUN-перехвата на L3):
1. Браузер отправляет HTTP-заголовок: `User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)...`.
2. Однако TCP-соединение с веб-сайтом инициирует **серверный узел** (Linux VPS).
3. Веб-сервер получает пакеты со стеком Linux: `Initial TTL = 64`, Linux TCP Options Order, Linux MSS.
4. **Аномалия:** `User-Agent = Windows`, но `TCP/IP Stack = Linux`. Антифрод-системы (Cloudflare Bot Management, Akamai Bot Manager, DataDome) немедленно маркируют соединение флагом `OS_MISMATCH` и выдают проверку капчей (Cloudflare Turnstile) или блокируют сессию.

### 2.5. Рассинхронизация временных зон, языка и аппаратных отпечатков

#### 2.5.1. Извлечение Timezone через JavaScript (`Intl`, `Date`)

Даже если IP-адрес указывает на Франкфурт (Германия), встроенные JavaScript API браузера выполняются в контексте хостовой операционной системы:

```javascript
// Определение системной временной зоны хоста
const systemTimezone = Intl.DateTimeFormat().resolvedOptions().timeZone;
// Пример возврата: "Europe/Moscow" или "Asia/Yekaterinburg"

// Определение смещения в минутах относительно UTC
const timezoneOffset = new Date().getTimezoneOffset();
// Для UTC+3 возвращает: -180
```

Антифрод-система сравнивает часовой пояс IP-адреса (по базе MaxMind GeoIP: для IP Франкфурта это `Europe/Berlin`, смещение UTC+1 / UTC+2) со значением `Intl.DateTimeFormat()`. Расхождение свидетельствует о работе через VPN/прокси.

#### 2.5.2. Языковой стек (`navigator.languages`, `Accept-Language`)

```javascript
// Языковые предпочтения в браузере
console.log(navigator.languages); // ["ru-RU", "ru", "en-US", "en"]
```
Если IP принадлежит Нидерландам (`nl-NL`), а браузер запрашивает исключительно `ru-RU` с системным часовым поясом `Europe/Moscow`, коэффициент подозрительности (Fraud Score) возрастает на 30–50 пунктов.

#### 2.5.3. Скоринг несоответствий антифрод-системами

Современные антифрод-системы рассчитывают кумулятивный риск-скор:

$$\text{Risk Score} = w_1 \cdot \text{ASN\_Type} + w_2 \cdot \text{Timezone\_Mismatch} + w_3 \cdot \text{WebRTC\_Leak} + w_4 \cdot \text{TCP\_OS\_Mismatch}$$

Если серверный узел принадлежит датацентру (`hosting: true`), а часовой пояс расходится — доступ к банковским сервисам и ИИ-моделям блокируется.

## 3. Детекция и анализ защищенного DNS (DoH / DoT)

### 3.1. Векторы идентификации DoH/DoT внешними наблюдателями (DPI / ISP)

DNS-over-HTTPS (RFC 8484) и DNS-over-TLS (RFC 7858) созданы для шифрования DNS-трафика. Однако для сетевого наблюдателя (DPI ТСПУ, провайдер) сам факт использования DoH/DoT тривиально детектируется по ряду косвенных и прямых признаков.

#### 3.1.1. Детекция по известным IP/ASN публичных резолверов
Публичные шифрованные резолверы имеют статичные всемирно известные пулы IP-адресов Anycast:
- **Cloudflare:** `1.1.1.1`, `1.0.0.1`, `2606:4700:4700::1111`, `2606:4700:4700::1001`.
- **Google Public DNS:** `8.8.8.8`, `8.8.4.4`, `2001:4860:4860::8888`.
- **Quad9:** `9.9.9.9`, `149.112.112.112`, `2620:fe::fe`.
- **AdGuard DNS:** `94.140.14.14`, `94.140.15.15`.

Любая сессия к этим IP-адресам на порт 853 (DoT) или порт 443 (DoH) однозначно классифицируется DPI как шифрованный DNS. В РФ данные пулы регулярно подвергаются прямому троттлингу или сбросу TCP RST со стороны ТСПУ.

#### 3.1.2. Анализ TLS SNI и блокировка ECH в РФ
При установке HTTPS-соединения с DoH-сервером клиент отправляет расширение **Server Name Indication (SNI)** в открытом виде (если не согласован ECH):
- `dns.google`
- `cloudflare-dns.com`
- `dns.quad9.net`

DPI ТСПУ с 2023 года фильтрует соединения по указанным SNI. Попытка внедрения **Encrypted Client Hello (ECH)** для сокрытия SNI привела к тому, что осенью 2024 года ТСПУ начал массово блокировать TLS-хендшейки, содержащие расширение ECH (`encrypted_client_hello`), вызывая разрыв соединения.

#### 3.1.3. Поведенческие паттерны и канареечный домен `use-application-dns.net`

1. **Аномалия трафика:** На физическом интерфейсе клиента полностью пропадают запросы на стандартный порт `53 UDP/TCP`. Одновременно наблюдается постоянная фоновая HTTPS-сессия к единственному удаленному IP.
2. **Канареечный домен Firefox (Canary Domain):**
   - Mozilla Firefox при включении механизма DoH по умолчанию (режим TRR — Trusted Recursive Resolver) выполняет контрольный запрос к специальному домену:
     `use-application-dns.net`.
   - Если корпоративный шлюз или DPI возвращает ответ `NXDOMAIN` (домен не существует) или с ошибкой `SERVFAIL`, Firefox **автоматически отключает DoH** и возвращается к незашифрованному системному DNS. Это легитимный механизм сигнализации (RFC draft), активно эксплуатируемый цензорами для принудительного отключения DoH у пользователей.

### 3.2. Методика верификации шифрования DNS тестовыми платформами

Как тестовые платформы (например, Cloudflare Browser Check, BrowserLeaks) определяют, защищен ли DNS пользователя:
1. Тестовая страница запрашивает через AJAX уникальный субдомен, принадлежащий инфраструктуре Cloudflare, например:
   `https://<uuid>.is-doh.cloudflare.com/cdn-cgi/trace`.
2. Граничный сервер Cloudflare проверяет внутренний мета-контекст входящего запроса:
   - Через какой внутренний транспорт поступил предварительный DNS-запрос на имя `<uuid>.is-doh.cloudflare.com`?
   - Если запрос пришел из внутренней очереди DoH-демона (1.1.1.1) с признаком TLS — выставляется флаг `doh: true`.
   - Если запрос пришел через классический UDP-рекурсор — выставляется `doh: false`.

## 4. Обзор публичных платформ аудита утечек и оценки репутации IP

### 4.1. Сервисы комплексного аудита утечек

#### 4.1.1. BrowserLeaks (browserleaks.com)
Один из старейших и наиболее авторитетных инструментов аудита браузерной приватности (автор — Denis Sinegubko).
* **WebRTC Test:** детальный аудит кандидатов ICE. Показывает локальные адреса (IPv4/IPv6), публичный IPv4/IPv6, проверяет наличие TCP/UDP кандидатов и состояние поддержки mDNS (сокрытие локальных IP хешами `.local`).
* **DNS Leak Test:** использует параллельный опрос 50+ уникальных поддоменов, строит граф upstream-резолверов с указанием их ASN, страны и обратных PTR-записей.
* **IP Address Test:** детектирование прямого IP, параметров MTU/MSS, обратного DNS, наличия открытых прокси-портов.
* **Аппаратные фингерпринты:** Canvas Fingerprinting, WebGL Report, AudioContext Fingerprint, Font Enumeration (детектирование списка системных шрифтов), Client Rects.

#### 4.1.2. IPLeak.net (от AirVPN)
Комплексный сканер утечек, разработанный провайдером AirVPN.
* **Torrent Address Detection:** уникальный инструмент проверки реального IP в P2P-сетях.
  - Пользователю генерируется персональная `magnet:` ссылка с уникальным infohash.
  - Клиент добавляет ссылку в BitTorrent-клиент (uTorrent, qBittorrent, Transmission).
  - Трекер IPLeak фиксирует реальный IP-адрес, с которого BitTorrent-клиент обращается за метаданными торрента. Это выявляет ситуации, когда веб-браузер работает через прокси, а торрент-клиент качает напрямую.
* **WebSocket Leak Test:** инициирует исходящие WebSocket-соединения (`ws://` / `wss://`) для проверки перехвата сокетов нестандартных транспортов.

#### 4.1.3. IPHey (iphey.com)
Платформа скоринга цифрового отпечатка, ориентированная на оценку доверия к пользователю со стороны антифрод-систем.
* Формирует агрегированный вердикт: **Reliable** (Надежный) или **Unreliable** (Подозрительный).
* Анализирует 5 ключевых доменов:
  1. **Browser:** подлинность User-Agent, отсутствие артефактов автоматизации (Selenium, Puppeteer, Playwright).
  2. **Location:** соответствие IP-геолокации и временной зоны.
  3. **IP:** тип сети (ISP, Hosting, Business), наличие в черных списках спама.
  4. **System:** шрифты, системные языки, ОС.
  5. **Hardware:** рендерер видеокарты (WebGL UNMASKED_RENDERER — реальный ли GPU или виртуальный драйвер SwiftShader/llvmpipe).

#### 4.1.4. CreepJS и PixelPrivacy
Продвинутые сканеры эмуляции и манипуляций с JavaScript API:
* **CreepJS (abrahamjuliot/creepjs):** глубокий аудит модификации прототипов JS-объектов. Выявляет использование антидетект-браузеров (AdsPower, Dolphin Anty, Multilogin) по мельчайшим аномалиям реализации `navigator`, `WebGLRenderingContext`, Worker context leaks.
* **PixelPrivacy:** аудит искажения пикселей при рендеринге канваса (noise injection).

#### 4.1.5. Cloudflare Connection & ECH Check
* Адрес проверки: `cloudflare.com/ssl/encrypted-sni/` (а также внутренний endpoint `1.1.1.1/help`).
* Проверяет 4 ключевых параметра безопасности соединения:
  1. **Secure DNS:** факт разрешения доменов через DoH/DoT.
  2. **DNSSEC:** валидация криптографических подписей зон DNS.
  3. **TLS 1.3:** использование актуальной версии криптографического протокола.
  4. **Encrypted Client Hello (ECH):** шифрование SNI в TLS-хендшейке.

### 4.2. Платформы оценки репутации IP и Fraud Score

Для сервисов уровня OpenAI, Anthropic, Netflix, банков и платежных систем ключевым фактором допуска пользователя является не факт шифрования трафика, а **репутация его выходного IP-адреса**.

#### 4.2.1. IPQualityScore (IPQS)
* Рассчитывает показатель **Fraud Score** от 0 до 100 (где 0 — идеальный чистый IP, 100 — гарантированный бот/ботнет/мошенник).
* Возвращает структурированные флаги:
  - `vpn: true/false` — факт принадлежности к коммерческим VPN-сетям.
  - `proxy: true/false` — открытый или приватный прокси.
  - `tor: true/false` — выходная нода сети Tor.
  - `active_vpn: true/false` — зафиксирована ли активная VPN-сессия прямо сейчас.
  - `recent_abuse: true/false` — фиксировались ли с этого IP спам, брутфорс, DDoS в последние 72 часа.
  - `connection_type: "Data Center" | "Residential" | "Mobile"`.

#### 4.2.2. MaxMind GeoIP2 / minFraud (Anonymous IP Database)
Отраслевой золотой стандарт для e-commerce и облачных сервисов.
* База данных `GeoIP2 Anonymous IP` содержит поля:
  - `is_anonymous`: глобальный признак сокрытия IP.
  - `is_anonymous_vpn`: коммерческий VPN.
  - `is_hosting_provider`: IP-адрес принадлежит хостинг-провайдеру/датацентру.
  - `is_public_proxy`: публичный прокси-сервер.
  - `is_tor_exit_node`: выходной узел Tor.
  - `is_residential_proxy`: резидентный прокси (ботнет или домашний IP).

#### 4.2.3. Spur.us
Самый детализированный в индустрии сервис атрибуции прокси и VPN.
* Отслеживает коммерческие резидентные прокси-сети (Bright Data, Oxylabs, Smartproxy, IPRoyal).
* Способен различать, через какой конкретно сервис туннелируется трафик (например: "ProtonVPN", "Mullvad", "Tailscale", "WARP").

#### 4.2.4. Scamalytics
* Специализируется на оценке риска мошенничества для дейтинговых сервисов и финтеха.
* Предоставляет `Fraud Score (0–100)` и классификацию риска: `Low`, `Medium`, `High`, `Very High`.

#### 4.2.5. ip-api.com (Pro) и классификация ASN: Datacenter vs Residential

Сравнение типов автономных систем:

| Параметр | Datacenter / Hosting ASN (VPS) | Residential ASN (Домашний провайдер) | Mobile ASN (Сотовые операторы) |
| :--- | :--- | :--- | :--- |
| **Примеры ASN** | AS24940 (Hetzner), AS14061 (DigitalOcean), AS16276 (OVH) | AS12389 (Ростелеком), AS3352 (Iberbanda), AS7922 (Comcast) | AS25159 (Tele2), AS28849 (VimpelCom), AS577 (Bell) |
| **Поле `hosting` в ip-api** | `true` | `false` | `false` |
| **Отношение антифрода** | **Крайне жесткое:** автоматическое требование Cloudflare Turnstile / запрет регистрации в ChatGPT / Claude | **Максимальное доверие:** минимальный риск капчи | **Максимальное доверие:** динамический CGNAT-пул |
| **Поведение при стриминге** | Netflix, Кинопоиск, Spotify часто блокируют по маске | Полная доступность стриминговых библиотек | Полная доступность |

> **Критический вывод для `vpn-installer`:** При развертывании VPN на стандартном VPS (Hetzner, OVH) трафик пользователя гарантированно помечается как `hosting: true`. Для обхода блокировок сервисов вроде OpenAI и Claude на сервере необходимо маршрутизировать трафик таких сервисов через промежуточный эгресс-шлюз с чистой репутацией — нативный **Cloudflare WARP Outbound** (как детально описано в нашем смежном исследовании архитектуры клиент-сервер).

## 5. Готовые открытые инструменты, скрипты и PoC

### 5.1. CLI-скрипты для автоматизированного тестирования DNS-утечек

Для интеграции автоматических тестов в консольные клиенты и сценарии CI/CD разработаны легковесные скрипты на Bash и Python 3, работающие с открытым API `bash.ws/dnsleak`.

#### Вариант на Bash (зависимости: `curl`, `jq` или базовый парсер)

```bash
#!/usr/bin/env bash
# dns_leak_test.sh - Проверка DNS-утечек через консоль
set -euo pipefail

RED='\033[0;31m'
GREEN='\033[0;32m'
YELLOW='\033[1;33m'
NC='\033[0m'

echo -e "${YELLOW}=== Запуск аудита DNS-утечек ===${NC}"

# 1. Получение уникального ID сессии тестирования
SESSION_ID=$(curl -s "https://bash.ws/dnsleak/test" | grep -oE '[a-f0-9]{32}' | head -n1 || true)
if [ -z "$SESSION_ID" ]; then
    # Fallback генерация ID если парсинг не сработал
    SESSION_ID=$(od -x /dev/urandom | head -1 | awk '{print $2$3$4$5}')
fi

echo -e "Идентификатор теста: ${SESSION_ID}"
echo -e "Отправка серии DNS-запросов через системный резолвер..."

# 2. Инициация 10 параллельных запросов к уникальным поддоменам
for i in $(seq 1 10); do
    TARGET_DOMAIN="${i}.${SESSION_ID}.bash.ws"
    # Резолвим через системную утилиту ping или getent/nslookup
    ping -c 1 -W 1 "${TARGET_DOMAIN}" > /dev/null 2>&1 || true
done

# Пауза для сбора статистики на authoritative NS
sleep 2

# 3. Запрос результатов
RESULT_JSON=$(curl -s "https://bash.ws/dnsleak/test/${SESSION_ID}?json")

echo -e "\n${YELLOW}=== Обнаруженные DNS-резолверы ===${NC}"
echo "$RESULT_JSON" | python3 -c '
import sys, json

data = json.load(sys.stdin)
dns_servers = [item for item in data if item.get("type") == "dns"]
ip_servers = [item for item in data if item.get("type") == "ip"]

print("Ваш публичный IP (по версии теста):")
for ip in ip_servers:
    print(f" -> IP: {ip.get(\"ip\")} | Страна: {ip.get(\"country_name\")} | Провайдер: {ip.get(\"asn\")}")

print("\nUpstream DNS-серверы, выполнявшие запросы:")
for dns in dns_servers:
    print(f" -> DNS IP: {dns.get(\"ip\")} | Страна: {dns.get(\"country_name\")} | ASN: {dns.get(\"asn\")}")

# Простейшая эвристика утечки
```

```python
#!/usr/bin/env python3
"""
custom_dns_leak_server.py
Легковесный Authoritative DNS сервер с сохранением IP рекурсивных резолверов.
Зависимость: pip install dnslib aiohttp
"""

import asyncio
from dnslib import DNSRecord, DNSHeader, RR, A, QTYPE
from dnslib.server import BaseCallbackHandler
import sqlite3
import time

DB_FILE = "/var/log/dns_leaks.db"

def init_db():
    with sqlite3.connect(DB_FILE) as conn:
        conn.execute("""
            CREATE TABLE IF NOT EXISTS queries (
                uuid TEXT,
                resolver_ip TEXT,
                subdomain TEXT,
                timestamp INTEGER
            )
        """)
init_db()

class LeakDetectionHandler(BaseCallbackHandler):
    def resolve(self, request, handler):
        reply = request.reply()
        qname = str(request.q.qname).strip(".").lower()
        resolver_ip = handler.client_address[0]
        
        # Ожидаемый формат: <part>.<uuid>.leak.myvpn.org
        parts = qname.split(".")
        if len(parts) >= 4 and parts[-3:] == ["leak", "myvpn", "org"]:
            test_uuid = parts[-4]
            # Запись факта обращения рекурсивного DNS
            with sqlite3.connect(DB_FILE) as conn:
                conn.execute(
                    "INSERT INTO queries VALUES (?, ?, ?, ?)",
                    (test_uuid, resolver_ip, qname, int(time.time()))
                )
        
        # Возвращаем заглушку A-записи
        reply.add_answer(RR(qname, QTYPE.A, rdata=A("127.0.0.1"), ttl=10))
        return reply

# Для запуска требуется запуск на порту 53: sudo python3 custom_dns_leak_server.py
```

##### Архитектурный разбор ключевых директив:

1. **`strict_route: true` на TUN-интерфейсе:**
   - **Для Windows:** задействует Wintun драйвер со строгой изоляцией таблицы маршрутизации, полностью деактивируя Windows Smart Multi-Homed Name Resolution (SMHNR). Запросы физически не могут уйти мимо Wintun.
   - **Для Linux:** настраивает правила маршрутизации политик `ip rule` и маркировку пакетов `fwmark`, гарантируя, что трафик приложений не уйдет через физический шлюз.
2. **`port: [3478, 5349]` и `protocol: "stun"` -> `outbound: "block"`:**
   - Полностью нейтрализует WebRTC IP Leak! Если браузер пытается отправить STUN Binding Request для обнаружения `srflx` кандидата, пакет мгновенно отбрасывается ядром `sing-box`. Браузер остается только с безопасным локальным `host` кандидатом (`.local` mDNS) или переходит на relay-кандидат.
3. **`strategy: "ipv4_only"` и `ip_version: 6` -> `outbound: "block"`:**
   - Закрывает IPv6 Dual-Stack утечку, если сервер не поддерживает полноценный IPv6-туннель.
   - DNS-сервер sing-box блокирует AAAA-запросы (`dns-block`), заставляя Happy Eyeballs использовать исключительно IPv4.
   - Все случайные IPv6-пакеты дропаются ядром маршрутизации.
4. **`protocol: "dns"` и `port: 53` -> `outbound: "dns-out"`:**
   - Жесткий перехват всех системных DNS-пакетов. Любая программа, пытающаяся отправить запрос на `8.8.8.8:53` или провайдерский DNS в обход, принудительно перехватывается и направляется во встроенный DNS-движок sing-box (`dns-remote` через туннель).
5. **`utls.fingerprint: "chrome"`:**
   - Маскирует ClientHello под легитимный браузер Google Chrome, исключая аномалии отпечатков TLS (JA3/JA4).

```go
	}

}
```

   - **RFC 1035:** *Domain Names - Implementation and Specification*.
   - **RFC 7858:** *Specification for DNS over Transport Layer Security (DNS-over-TLS)*.
   - **RFC 8484:** *DNS Queries over HTTPS (DoH)*.
   - **RFC 8305:** *Happy Eyeballs Version 2: Better Connectivity Using Concurrency* (IPv6/IPv4 Dual-Stack race).
   - **RFC 9460:** *Service Binding and Parameter Specification via the DNS (SVCB and HTTPS Resource Records)*.
