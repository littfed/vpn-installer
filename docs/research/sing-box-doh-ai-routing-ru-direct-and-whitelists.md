## 1. Архитектура подсистемы DNS в Sing-box (DoH, DoT, DoH3)

### 1.1. Конфигурация подсистемы `dns`

В ядре `sing-box` (начиная с версии 1.8 и включая современные ветки 1.9–1.11+) подсистема `dns` представляет собой автономный мультиплексирующий DNS-маршрутизатор. Она работает в тесной связке с сетевым роутером (`route`), но оперирует на собственном уровне абстракции до установления TCP/UDP сессий.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   АРХИТЕКТУРА ПОДСИСТЕМЫ DNS SING-BOX                  │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │ DNS Query (UDP/TCP/Inbound TUN)
                                     ▼
                      ┌─────────────────────────────┐
                      │    DNS Router (dns.rules)   │
                      └──────────────┬──────────────┘
                                     │
         ┌───────────────────────────┼───────────────────────────┐
         │ (ru domains)              │ (blocked / AI domains)    │ (other / fallback)
         ▼                           ▼                           ▼
┌──────────────────┐       ┌──────────────────┐        ┌──────────────────┐
│ Server: ru-dns   │       │ Server: remote   │        │ Server: direct   │
│ Address: DoH/DoT │       │ Address: DoH/DoH3│        │ Address: local   │
│ Detour: direct   │       │ Detour: proxy    │        │ Detour: direct   │
└────────┬─────────┘       └────────┬─────────┘        └────────┬─────────┘
         │                           │                          │
         ▼                           ▼                          ▼
Local ISP/Yandex DNS        Cloudflare / Google         ISP Default DNS
(Optimal Geo-IP RU)        (Uncensored, No Leak)        (Bootstrap Only)
```

Базовая спецификация блока `dns`:

```json
{
  "dns": {
    "servers": [
      {
        "tag": "dns-remote",
        "address": "https://1.1.1.1/dns-query",
        "address_resolver": "dns-local",
        "address_strategy": "prefer_ipv4",
        "strategy": "prefer_ipv4",
        "detour": "proxy"
      },
      {
        "tag": "dns-direct",
        "address": "https://77.88.8.8/dns-query",
        "address_resolver": "dns-local",
        "address_strategy": "prefer_ipv4",
        "strategy": "prefer_ipv4",
        "detour": "direct"
      },
      {
        "tag": "dns-local",
        "address": "local",
        "detour": "direct"
      },
      {
        "tag": "dns-block",
        "address": "rcode://success"
      }
    ],
    "rules": [
      {
        "outbound": "any",
        "server": "dns-direct"
      },
      {
        "rule_set": "geosite-category-ads-all",
        "server": "dns-block",
        "disable_cache": true
      },
      {
        "rule_set": ["geosite-ru", "geosite-yandex", "geosite-vk"],
        "server": "dns-direct"
      },
      {
        "rule_set": ["geosite-openai", "geosite-anthropic", "geosite-google"],
        "server": "dns-remote"
      }
    ],
    "final": "dns-remote",
    "strategy": "prefer_ipv4",
    "independent_cache": true,
    "reverse_mapping": true,
    "client_subnet": "77.88.8.0/24"
  }
}
```

#### Ключевые директивы конфигурации:
1. `servers`: Массив апстрим-серверов.
   - `address`: URI протокола DNS. Поддерживаются форматы:
     - Обычный UDP/TCP: `tcp://8.8.8.8`, `udp://8.8.8.8`, `8.8.8.8` (по умолчанию UDP с фолбэком на TCP).
     - DNS-over-HTTPS (DoH): `https://1.1.1.1/dns-query` (HTTP/2 по умолчанию).
     - DNS-over-HTTP/3 (DoH3): `h3://cloudflare-dns.com/dns-query` (QUIC транспорт, устойчивый к TCP Head-of-Line Blocking).
     - DNS-over-TLS (DoT): `tls://1.1.1.1` или `tls://dns.google`.
     - DNS-over-QUIC (DoQ): `quic://dns.adguard-dns.com`.
     - Системный/провайдерский резолвер: `local`.
     - Статический ответ (Null-routing / Sinkhole): `rcode://success` или `rcode://refused`.
     - Синтетический FakeIP пул: `fakeip`.
   - `address_resolver`: Тег сервера из списка `servers`, используемый для первичного разрешения доменного имени самого DNS-сервера (Bootstrap DNS). Если адрес DoH указан как `https://cloudflare-dns.com/dns-query`, sing-box сначала обратится к `address_resolver`, чтобы узнать IP-адрес `cloudflare-dns.com`.
   - `address_strategy`: Стратегия резолвинга адреса самого апстрима (`prefer_ipv4`, `prefer_ipv6`, `ipv4_only`, `ipv6_only`).
   - `strategy`: Стратегия разрешения доменов клиентов через данный апстрим. Для сетей РФ критически рекомендуется `prefer_ipv4` или `ipv4_only`, так как маршруты IPv6 на многих магистралях фильтруются ТСПУ с аномальным RTT или вовсе дропаются.
   - `detour`: Сетевой `outbound`, через который физически отправляется DNS-запрос. Запросы к `dns-remote` направляются через `proxy` (туннель VLESS/Reality/Shadowsocks), что исключает возможность их перехвата внутри РФ. Запросы к `dns-direct` уходят через `direct`.
   - `client_subnet`: Параметр EDNS Client Subnet (ECS, RFC 7871). Позволяет апстрим-серверу возвращать IP-адреса CDN, географически ближайшие к указанной подсети, предотвращая выдачу европейских нод для российских ресурсов при запросе через зарубежные серверы.
2. `rules`: Логика классификации запросов. Правила обрабатываются сверху вниз до первого совпадения. Поддерживаются `domain`, `domain_suffix`, `domain_keyword`, `rule_set`, `client_subnet`, `network`.
3. `final`: DNS-сервер по умолчанию, если ни одно правило не сработало.
4. `independent_cache`: Булево значение (`true`/`false`). При включении (`true`) кэш DNS изолируется для каждого апстрима из списка `servers`. Это предотвращает отравление общего кэша (DNS Cache Poisoning): если один сервер вернул заглушку ТСПУ, этот результат не будет использован при запросе через защищенный апстрим.
5. `reverse_mapping`: Булево значение (`true`/`false`). Сохраняет соответствие между разрешенным IP-адресом и исходным доменным именем в оперативной памяти sing-box. Когда приложение начинает передавать сетевые пакеты на полученный IP-адрес через L3 TUN, модуль маршрутизации может восстановить исходный домен и применить правила `rule_set` (например, `geosite-openai`), даже если приложение подключается напрямую по IP.

### 1.2. Механизмы ТСПУ: DNS Poisoning, UDP/TCP 53 Hijacking и методы их нейтрализации

Технические средства противодействия угрозам (ТСПУ), установленные на узлах всех операторов связи РФ по закону «о суверенном Рунете» (139-ФЗ, 90-ФЗ), используют комплексные методы цензуры на уровне DNS:

```
┌────────────────────────────────────────────────────────────────────────┐
│               МЕХАНИЗМЫ ДЕСТРУКТИВНОГО ВОЗДЕЙСТВИЯ ТСПУ НА DNS         │
├────────────────────────────────┬───────────────────────────────────────┤
│ Метод атаки ТСПУ               │ Физическая реализация                 │
├────────────────────────────────┼───────────────────────────────────────┤
│ 1. UDP 53 In-flight Spoofing   │ Внедрение поддельного DNS Response     │
│    (DNS Injection / Poisoning) │ с фальшивым A-record (IP заглушки или │
│                                │ 127.0.0.1) до ответа легитимного DNS  │
├────────────────────────────────┼───────────────────────────────────────┤
│ 2. Port 53 Full Interception   │ NAT-перенаправление любого UDP/TCP 53  │
│    (Transparent Proxy)         │ трафика на локальные DNS-резолверы    │
│                                │ провайдера с цензурными фильтрами     │
├────────────────────────────────┼───────────────────────────────────────┤
│ 3. Selective Drop / Blackhole  │ Сброс пакетов (DROP) к публичным DNS  │
│                                │ (1.1.1.1, 8.8.8.8, 9.9.9.9)           │
├────────────────────────────────┼───────────────────────────────────────┤
│ 4. DoH/DoT SNI Filtering       │ Блокировка TLS Handshake по SNI       │
│                                │ (cloudflare-dns.com, dns.google)      │
└────────────────────────────────┴───────────────────────────────────────┘
```

#### Архитектура нейтрализации DNS-атак в Sing-box:

1. **Полная изоляция стандартного порта 53:**
   В L3 TUN sing-box перехватывает все исходящие сетевые пакеты с целевым портом 53 UDP/TCP с помощью виртуального интерфейса и системных правил маршрутизации.
   Входящие пакеты маршрутизируются в специальный виртуальный DNS-стек sing-box:
   ```json
   {
     "type": "direct",
     "tag": "dns-out"
   }
   ```
   В секции `route.rules`:
   ```json
   {
     "protocol": "dns",
     "outbound": "dns-out"
   },
   {
     "port": 53,
     "outbound": "dns-out"
   }
   ```
   Это гарантирует, что ни один незашифрованный DNS-запрос от операционной системы или установленных программ не попадет в физическую сеть в открытом виде.

2. **Защита от спуфинга (Race Condition):**
   При открытом UDP 53 ТСПУ отправляет инжектированный ответ за 2–5 мс (так как ТСПУ физически находится на линии провайдера ближе, чем зарубежный сервер). Клиентская ОС принимает первый пришедший ответ и отбрасывает настоящий.
   Использование **DoH (HTTP/2 / HTTP/3)** и **DoT (TLS)** полностью исключает эту атаку:
   - Сессия защищена криптографическим протоколом TLS 1.3 с проверкой сертификата X.509.
   - ТСПУ не может сгенерировать валидный TLS-сертификат для домена апстрима. Любая попытка внедрения RST или фальшивого сертификата вызовет ошибку валидации в sing-box и не приведет к подмене IP.

### 1.3. Сравнительный анализ безопасных DoH/DoT upstream-провайдеров в РФ и обход их блокировок

В период 2022–2026 гг. Роскомнадзор и ТСПУ вели систематическую борьбу с независимыми зашифрованными протоколами DNS:

| Провайдер | IP-адреса | Доменные имена DoH / DoT | Статус блокировки в РФ | Поведение ТСПУ |
| :--- | :--- | :--- | :--- | :--- |
| **Cloudflare** | `1.1.1.1`, `1.0.0.1`, `2606:4700:4700::1111` | `cloudflare-dns.com`, `one.one.one.one` | **Заблокирован частично/массово** | IP `1.1.1.1` часто подвергается TCP SYN/UDP сбросу; SNI `cloudflare-dns.com` блокируется по DPI TLS ClientHello. |
| **Google Public DNS** | `8.8.8.8`, `8.8.4.4`, `2001:4860:4860::8888` | `dns.google` | **Периодические атаки / Нестабилен** | IP `8.8.8.8` открыт у большинства мобильных операторов для пинга, но DoT (порт 853) блокируется; DoH по SNI фильтруется выборочно. |
| **Quad9** | `9.9.9.9`, `149.112.112.112` | `dns.quad9.net` | **Блокируется на магистралях** | Порт 853 заблокирован полностью; DoH доступен через обходные IP. |
| **AdGuard DNS** | `94.140.14.14`, `94.140.15.15` | `dns.adguard-dns.com` | **Выборочная фильтрация** | Официальный домен периодически подвергается SNI-блокировкам. DoQ (QUIC порт 784/853) режется. |
| **Яндекс 312 / DNS** | `77.88.8.8`, `77.88.8.1` | `common.dot.dns.yandex.net`, `dns.yandex.ru` | **Полностью доступен** | Легитимный российский сервис. Не блокируется, идеален для прямого резолвинга RU-доменов. |

#### Методы обхода блокировок DoH/DoT внутри РФ:

1. **Резолвинг DoH через удаленный защищенный туннель (`detour: "proxy"`):**
   Это фундаментальный и наиболее надежный метод:
   ```json
   {
     "tag": "dns-remote",
     "address": "https://1.1.1.1/dns-query",
     "detour": "proxy"
   }
   ```
   В этой схеме пакеты DoH к Cloudflare инкапсулируются в шифрованный трафик VLESS-Reality или Shadowsocks-2022. ТСПУ видит только сессию к зарубежному VPS и не имеет технической возможности определить, что внутри туннеля передаются запросы к `1.1.1.1`.

2. **Прямое указание IP-адреса в URL DoH (без SNI-домена):**
   В sing-box можно использовать адрес вида `https://1.1.1.1/dns-query` вместо `https://cloudflare-dns.com/dns-query`. При этом TLS-рукопожатие выполняет проверку IP-SAN сертификата Cloudflare, избегая триггера ТСПУ на строковое имя `cloudflare-dns.com` в открытом SNI (если IP не заблокирован напрямую по подсети).

3. **Использование нестандартных портов и альтернативных Anycast-адресов Cloudflare:**
   Cloudflare поддерживает DoH на резервных IP-адресах, которые редко попадают в списки прямой блокировки:
   - `162.159.36.1`
   - `162.159.46.1`
   - `172.64.36.1`
   - `172.64.36.2`

4. **Использование DoH3 (DNS-over-HTTP/3 на базе QUIC):**
   ```json
   {
     "tag": "dns-remote-h3",
     "address": "h3://162.159.36.1/dns-query",
     "strategy": "prefer_ipv4",
     "detour": "direct"
   }
   ```
   HTTP/3 передается через UDP 443. Если UDP на данном провайдере не подвергается тотальному дропу, протокол QUIC обеспечивает значительно более быстрое шифрованное соединение за счет 0-RTT рукопожатия и отсутствия блокировок по TCP RST.

### 1.4. Сравнительное исследование: FakeIP (`fakeip`) vs RealIP в L3 TUN sing-box

В режиме перехвата трафика сетевого уровня (L3 TUN) sing-box может использовать две принципиально разные парадигмы обработки доменных имен:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        REAL IP РЕЖИМ (REAL-DNS)                        │
└────────────────────────────────────────────────────────────────────────┘
App -> DNS Query -> [sing-box DNS] -> Remote DoH -> Real IP (e.g. 104.18.2.1)
App <- Real IP  <----------------------------------
App -> TCP Connect to 104.18.2.1:443 ------------------------------------>
[sing-box TUN] -> Sniff TLS SNI -> Route Decision -> Outbound Proxy

┌────────────────────────────────────────────────────────────────────────┐
│                        FAKE IP РЕЖИМ (SYNTHETIC)                       │
└────────────────────────────────────────────────────────────────────────┘
App -> DNS Query -> [sing-box DNS] -> Instant Fake IP (e.g. 198.18.0.42)
App <- Fake IP (0 ms RTT) <---------- (Cached map: 198.18.0.42 = openai.com)
App -> TCP Connect to 198.18.0.42:443 ----------------------------------->
[sing-box TUN] -> Instant Mapping to Domain -> Route to Proxy -> Remote DNS
```

#### Глубокий сравнительный анализ:

| Критерий | FakeIP (`fakeip`) | RealIP (Стандартный резолв) |
| :--- | :--- | :--- |
| **Задержка первого подключения (RTT)** | **Минимальная (0 мс DNS RTT)**. Ответ выдается локально из синтетического адресного пула `198.18.0.0/15` мгновенно. | **Высокая (1–2 RTT)**. Клиент вынужден ждать ответа от удаленного DoH-сервера перед установкой TCP-сессии. |
| **Предотвращение DNS-Leak** | **Абсолютное**. Клиентская ОС вообще не генерирует внешние DNS-запросы для проксируемых ресурсов. | Требует строгой изоляции портов 53 и жесткой привязки апстримов к защищенным аутбаундам. |
| **Географическая оптимизация (CDN)** | Разрешение домена выполняется на удаленном сервере (VPS/Proxy). Клиент получает IP-адрес CDN, ближайший к выходу прокси. | Локальные запросы через `dns-direct` получают корректные локальные CDN-адреса, но для проксируемых ресурсов возможны неоптимальные маршруты. |
| **Совместимость с Direct-соединениями** | **Ограниченная / Требует осторожности**. Если приложение кэширует FakeIP, а маршрут переключается на `direct`, пакеты на `198.18.0.x` не дойдут без перезаписи. | **Идеальная**. Любое прямое соединение использует настоящий публичный IP-адрес хоста. |
| **DNSSEC и специфичные валидаторы** | **Несовместимо**. Локальные валидаторы DNSSEC в ОС или приложениях будут отклонять синтетические ответы. | Полная совместимость при поддержке со стороны выбранного DoH/DoT апстрима. |
| **Peer-to-Peer (WebRTC, BitTorrent, VoIP)** | Может нарушать STUN/TURN протоколы, где требуется реальный IP пира. | Работает прозрачно без искажения сетевой топологии. |
| **Поведение при падении прокси** | Приложение думает, что DNS работает, но TCP-соединение зависает на этапе хэндшейка. | Приложение сразу получает ошибку DNS (NXDOMAIN/Timeout). |

#### Спецификация конфигурации FakeIP в Sing-box:

      {

### 2.1. Механизмы и векторы блокировок ИИ-провайдеров

Ведущие мировые разработчики LLM (OpenAI, Anthropic, Google, Cursor, Perplexity) внедрили многоуровневые системы комплаенса и защиты периметра:

```
┌────────────────────────────────────────────────────────────────────────┐
│             МНОГОУРОВНЕВАЯ СИСТЕМА ФИЛЬТРАЦИИ ИИ-СЕРВИСОВ              │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Geo-IP & Sanctions Compliance (OFAC: Блокировка российских IP)      │
│ 2. Datacenter ASN Blacklisting (Бан Hetzner, OVH, DigitalOcean, Vultr) │
│ 3. Cloudflare Turnstile / Bot Management (WAF анализ поведения браузера│
│ 4. TLS/JA3/JA4 Fingerprinting (Детекция Go-crypto, Python-requests)    │
│ 5. Account Risk Scoring (Корреляция номера телефона, биллинга и IP)    │
└────────────────────────────────────────────────────────────────────────┘
```

#### Детальный разбор векторов детекции:

1. **ASN Blacklisting (Датацентровые IP):**
   - **Hetzner (AS24940), OVH (AS16276), DigitalOcean (AS14061), Scaleway, Linode/Akamai, Oracle Cloud.**
   - Большинство пользователей развертывают личные прокси на недорогих серверах Hetzner или OVH в Европе. OpenAI и Anthropic заносят диапазоны IP этих провайдеров в глобальный черный список.
   - *Симптомы:*
     - OpenAI: Ошибка `Access denied. Error code 1020` или бесконечный цикл Cloudflare Turnstile ("Verify you are human").
     - Anthropic (Claude.ai): Ошибка `App unavailable in your country` или HTTP 403 Forbidden даже при локации сервера в Германии или Нидерландах.
     - Google Gemini / AI Studio: Ошибка `Gemini is not supported in your country`.

2. **Cloudflare Turnstile и WAF Score:**
   - Сервисы ChatGPT и Claude защищены Cloudflare WAF.
   - Cloudflare присваивает каждому входящему TCP/TLS-соединению показатель Threat Score (от 0 до 100). Запросы с датацентровых IP автоматически получают высокий базовый риск (score > 40), вызывая жесткую проверку капчи или прямой сброс сессии.

3. **TLS ClientHello Fingerprint (JA3 / JA4):**
   - Десктопные клиенты (например, Cursor IDE, Claude Desktop, Copilot в VS Code) используют встроенные сетевые стеки Electron/Node.js или специализированные HTTP-клиенты. При проксировании через промежуточные ноды с модификацией заголовков или несогласованным TLS-отпечатком WAF моментально распознает аномалию.

### 2.3. Интеграция Cloudflare WARP как Egress Outbound (`type: wireguard`)

#### Почему Cloudflare WARP решает проблему ASN-банов?
Cloudflare WARP — это сеть Anycast VPN, работающая на базе протокола WireGuard. Весь исходящий трафик WARP маршрутизируется через собственную глобальную сеть Cloudflare (AS13335).
- **Turnstile Trust:** Сеть Cloudflare WAF рассматривает IP-адреса Cloudflare WARP как легитимные пользовательские подключения, минимизируя Threat Score до 0.
- **Чистый Residential/Egress Pool:** IP-адреса WARP не находятся в черных списках датацентров у OpenAI и Anthropic.
- **Географическая привязка:** WARP автоматически выдает IP-адрес ближайшей к серверу локации Cloudflare (например, Франкфурт, Хельсинки, Амстердам), которая входит в список стран, официально поддерживаемых ИИ-сервисами.

```
┌────────────────────────────────────────────────────────────────────────┐
│             ТОПОЛОГИЯ СЕЛЕКТИВНОГО EGRESS ПРОКСИРОВАНИЯ ИИ             │
└────────────────────────────────────────────────────────────────────────┘

 [Клиент в РФ]
       │
       │ (VLESS Reality / Shadowsocks-2022 через ТСПУ)
       ▼
 [VPS Сервер (Hetzner / OVH)]
       │
       ├─► Обычный интернет ───────────► Direct Outbound (IP Hetzner)
       │
       └─► Трафик к OpenAI/Claude/Gemini
                 │
                 ▼
          [WireGuard Outbound]
                 │
                 ▼ (Внутренний туннель Anycast)
          [Cloudflare WARP AS13335]
                 │
                 ▼
          [OpenAI / Claude / Gemini] (Turnstile OK, ASN Clean!)
```

---

### 2.4. Регистрация в API Cloudflare WARP и генерация WireGuard-ключей

Для прямого подключения sing-box к Cloudflare WARP без установки официального демона `warp-cli` используется нативный outbound `type: wireguard`.

Для авторизации в API Cloudflare требуются следующие параметры:
1. `private_key`: Закрытый ключ WireGuard (Base64).
2. `public_key`: Открытый ключ пира Cloudflare (`bmXOC+F1FxEMF9dyiK2H5/1SUtzH0JuVo51h2wPfgyo=`).
3. `local_address`: Назначенные Cloudflare внутренние адреса IPv4 (`172.16.0.2/32`) и IPv6 (`2606:4700:110:.../128`).
4. `reserved`: **Критический параметр!** 3-байтовый массив целых чисел (или Base64-строка из 3 байт), уникальный идентификатор клиента Cloudflare в расширенном заголовке WireGuard Handshake Init. Без передачи правильного `reserved` соединение отклоняется фаерволом Cloudflare!

## 3. Маршрутизация трафика в РФ напрямую (Bypass Russia / Split Tunneling)

### 3.1. Проблема доступности сервисов РФ при активном зарубежном VPN

При постоянном использовании зарубежного VPN пользователи в РФ сталкиваются с серьезными деградациями и отказами в обслуживании:

```
┌────────────────────────────────────────────────────────────────────────┐
│              ПРОБЛЕМЫ ДОСТУПА К RU-СЕРВИСАМ ЧЕРЕЗ ЗАРУБЕЖНЫЙ VPN       │
├────────────────────────────────┬───────────────────────────────────────┤
│ Проблема                       │ Практические последствия             │
├────────────────────────────────┼───────────────────────────────────────┤
│ Геоблокировка зарубежных IP    │ Сервисы Госуслуг, ФНС, Mos.ru, Сбер, │
│ на стороне инфраструктуры РФ   │ Т-Банк, ВТБ, Кинопоиск, Авито, Ozon   │
│                                │ блокируют доступ с иностранных IP     │
│                                │ для защиты от DDoS-атак и сканирования│
├────────────────────────────────┼───────────────────────────────────────┤
│ Сертификаты Минцифры РФ        │ Российские государственные и банков-  │
│ (Russian Trusted Root CA)      │ ские сайты используют национальные SSL│
│                                │ сертификаты. Проксирование через узлы │
│                                │ без доверенных сертификатов вызывает  │
│                                │ критические TLS-ошибки в браузерах    │
├────────────────────────────────┼───────────────────────────────────────┤
│ Деградация RTT и скорости      │ Маршрут: Москва -> Франкфурт -> Москва│
│ локальных CDN                  │ увеличивает пинг с 3-5 мс до 60-90 мс,│
│                                │ а видеопотоки (Яндекс, VK, Кинопоиск) │
│                                │ отдаются с низким битрейтом           │
└────────────────────────────────┴───────────────────────────────────────┘
```

Единственным корректным архитектурным решением является **Split-Tunneling (раздельное туннелирование)**, при котором трафик к российским ресурсам идет напрямую через локального провайдера, а весь остальной — через защищенный туннель.

### 3.2. Раздельная маршрутизация DNS (Split DNS) для доменов `.ru` / `geosite-ru`

Если направить DNS-запрос для `yandex.ru` или `sberbank.ru` на зарубежный DNS (Cloudflare `1.1.1.1`), сервер вернет зарубежные Anycast IP-адреса серверов Яндекса в Европе или США, либо вообще вернет ошибку Geo-DNS.
Следовательно, запросы к российским доменам **обязаны** разрешаться через российские DNS-серверы:

```
               ┌──────────────────────────────────────┐
               │         DNS Query от приложения      │
               └──────────────────┬───────────────────┘
                                  │
                   ┌──────────────┴──────────────┐
                   │   Паттерн: geosite-ru ?     │
                   └──────┬───────────────┬──────┘
                     ДА   │               │   НЕТ
                          ▼               ▼
            ┌──────────────────┐    ┌──────────────────┐
            │ dns-direct (RU)  │    │ dns-remote       │
            │ Яндекс DoH       │    │ Cloudflare DoH   │
            │ Detour: direct   │    │ Detour: proxy    │
            └─────────┬────────┘    └─────────┬────────┘
                      │                       │
                      ▼                       ▼
            Выдача оптимального      Выдача незаблокированного
            российского CDN IP       зарубежного IP
```

### 3.3. Раздельная маршрутизация сетевых пакетов (Split Tunneling L3)

После того как DNS вернул IP-адрес, роутер sing-box оценивает пакет по цепочке правил `route.rules`:
1. Если домен принадлежит `geosite-ru` -> `outbound: direct`.
2. Если IP-адрес назначения входит в `geoip-ru` -> `outbound: direct`.
3. Если домен принадлежит `geosite-openai`, `geosite-anthropic` -> `outbound: proxy` (или `warp`).
4. Приватные подсети (`geoip-private`) -> `outbound: direct` или `block`.
5. Все остальное (заблокированные сайты, международный трафик) -> `outbound: proxy`.

### 3.4. Использование бинарных компилированных rule-set (`.srs`) и их источники

### 3.5. Тонкая настройка Inbound TUN: `auto_route`, `strict_route`, `sniff` и `sniff_override_destination`

Виртуальный интерфейс TUN перехватывает весь системный трафик ОС на 3-м сетевом уровне (IP). Для обеспечения безупречной работы без утечек критически важно правильно настроить следующие параметры:

```json
{
  "inbounds": [
    {
      "type": "tun",
      "tag": "tun-in",
      "interface_name": "tun0",
      "inet4_address": "172.19.0.1/30",
      "inet6_address": "fdfe:dcba:9876::1/126",
      "auto_route": true,
      "strict_route": true,
      "endpoint_independent_nat": true,
      "stack": "system",
      "sniff": true,
      "sniff_override_destination": true
    }
  ]
}
```

#### Назначение и физический смысл директив:

1. `auto_route: true`:
   - Автоматически создает и модифицирует таблицы маршрутизации ОС (`ip route` в Linux, Routing Table в Windows/macOS).
   - Направляет шлюз по умолчанию (`0.0.0.0/0` и `::/0`) в интерфейс TUN, автоматически сохраняя статический маршрут к вашему реальному прокси-серверу через физический сетевой интерфейс (предотвращая рекурсивную петлю маршрутизации).

2. `strict_route: true`:
   - Активирует режим строгой изоляции (системный Kill-Switch).
   - В Linux: добавляет правила маршрутизации политик (Policy Routing) и `ip rule`, которые подавляют утечки трафика в обход туннеля через альтернативные интерфейсы (например, при смене Wi-Fi на Ethernet или временной потере линка).
   - Сбрасывает любые некорректно маршрутизируемые пакеты (Blackhole).

3. `sniff: true`:
   - Включает инспекцию первых пакетов входящего TCP/UDP соединения на уровне L4–L7.
   - Извлекает доменное имя из:
     - TLS ClientHello (поле Server Name Indication — SNI).
     - Заголовка HTTP `Host`.
     - QUIC Initial Handshake.

4. `sniff_override_destination: true`:
   - **Самая мощная функция маршрутизации:** Когда приложение обращается к IP-адресу напрямую (или после FakeIP/RealIP), sing-box выполняет сниффинг SNI. Если обнаружено имя домена (например, `api.openai.com`), sing-box **перезаписывает адрес назначения сетевого контекста этим доменным именем**.
   - Это позволяет последующим правилам в `route.rules` применить матчинг по `geosite-openai`, даже если исходящий пакет был адресован на голый IP-адрес!

## 4. Преодоление сценариев «Белых списков» (Whitelisting / Шардауны внешних каналов в РФ)

### 4.1. Модель угроз и архитектура «Белых списков» ТСПУ

В условиях эскалации цензуры или проведения учений по «суверенизации Рунета» Роскомнадзор имеет техническую возможность перевести ТСПУ из режима «Черных списков» (Default Allow / Blacklisting) в режим **«Белых списков» (Default Deny / Whitelisting)**. Подобные сценарии многократно отрабатывались локально во время региональных блокировок интернета (Дагестан, Башкортостан, Якутия, Тува).

```
┌────────────────────────────────────────────────────────────────────────┐
│                   МОДЕЛЬ ФИЛЬТРАЦИИ ПРИ БЕЛЫХ СПИСКАХ                  │
├────────────────────────────────────────────────────────────────────────┤
│                     [Исходящий сетевой пакет из РФ]                     │
│                                    │                                   │
│                                    ▼                                   │
│                 Целевой IP находится в РФ (AS Ru-Net)?                 │
│                         /                      \                       │
│                   ДА   /                        \  НЕТ (Зарубежный IP) │
│                       ▼                          ▼                     │
│              [ПРОПУСК ТРАФИКА]          [ТСПУ ДЕФОЛТНЫЙ БАН]           │
│                                                  │                     │
│                           Целевой IP в Белом Списке ЦМУ ССОП?          │
│                                   /              \                     │
│                             ДА   /                \  НЕТ               │
│                                 ▼                  ▼                   │
│                        [Проверка SNI]         [DROP / RST]             │
│                         /            \                                 │
│                   Разрешен?         Запрещен?                          │
│                     /                    \                             │
│                    ▼                      ▼                            │
│            [ПРОПУСК СЕССИИ]          [DROP / RST]                      │
└────────────────────────────────────────────────────────────────────────┘
```

#### Характеристики режима «Белых списков»:
1. **Тотальный бан внешних IP-подсетей:** Все зарубежные серверы хостингов (Hetzner, OVH, DigitalOcean, AWS, GCP, Oracle) блокируются по BGP / IP Null-route.
2. **Исключения белого списка:** Разрешается доступ только к ограниченному перечню доверенных внешних ресурсов:
   - Критические сервисы обновлений мобильных ОС: Apple (`*.apple.com`, `*.icloud.com`), Google Play Services.
   - Корпоративные шлюзы и инфраструктурные сервисы: Microsoft Update/Teams, GitHub, Steam CDN.
   - Международные CDN, имеющие официальные соглашения о пиринге или обслуживание локальных компаний (Cloudflare, Akamai).
3. **Глубокая инспекция SNI:** Любое соединение на порт 443 без SNI или с неизвестным SNI сбрасывается TCP RST.
4. **Активное зондирование (Active Probing):** Если к разрешенному IP или через разрешенный SNI идет подозрительный трафик, ТСПУ параллельно инициирует проверочные TLS-хэндшейки с фальшивыми запросами к целевому серверу. Если сервер ведет себя не как оригинальный веб-сайт (например, возвращает пустой ответ или закрывает сокет), IP-адрес блокируется.

### 4.2. VLESS Reality с маскировкой под домены из гарантированного белого списка

Протокол **VLESS Reality** является фундаментальным решением для маскировки под разрешенные домены, так как он физически устраняет возможность обнаружения активным зондированием.

#### Механизм защиты Reality при активном зондировании:
В отличие от обычного VLESS-TLS или Trojan, где на сервере установлен собственный SSL-сертификат:
1. При легитимном подключении клиента sing-box, знающего `private_key` и `short_id`, сервер Reality расшифровывает заголовок и передает сессию в прокси-туннель.
2. Когда ТСПУ выполняет активное зондирование (Active Probe), посылая тестовые TLS ClientHello к вашему VPS, Reality-сервер **прозрачно проксирует (перенаправляет) весь TCP-хэндшейк на реальный целевой сервер маскировки** (например, `gateway.icloud.com` или `swx.cdn.skype.com`).
3. Зонд ТСПУ получает 100% подлинный сертификат Apple или Microsoft с валидной криптографической подписью и шифронаборами. В результате ТСПУ классифицирует узел как легитимный сервер из белого списка.

```
                   ┌───────────────────────────────────────┐
                   │    Входящий TLS Handshake на 443      │
                   └──────────────────┬────────────────────┘
                                      │
                       ┌──────────────┴──────────────┐
                       │ Валидный Short ID Reality?  │
                       └──────┬───────────────┬──────┘
                         ДА   │               │   НЕТ (Зонд ТСПУ)
                              ▼               ▼
                    [Туннель Sing-box]   [Прозрачный Forwarding]
                    (Шифрованный трафик) (на Apple / Microsoft)
                                                      │
                                                      ▼
                                         Подлинный TLS Сертификат
                                         (Атака ТСПУ провалена)
```

#### Критерии выбора маскировочного SNI для сценария «Белых списков»:
- Домен должен гарантированно входить в перечень жизненно важных сервисов (Apple APNs push-уведомления `gateway.icloud.com`, Microsoft Teams `teams.microsoft.com`, Steam `cdn.steamcommunity.com`).
- Сервер назначения должен обязательно поддерживать **TLS 1.3** и протокол **ALPN h2 (HTTP/2)**.
- Сервер назначения и ваш VPS должны иметь близкий RTT, чтобы время ответа хэндшейка не выдавало аномальную задержку.

### 4.3. WebSocket / gRPC через легитимные CDN (Cloudflare CDN, Fastly) с Fronting-маскировкой

Если в условиях шардауна прямой доступ к зарубежным IP заблокирован полностью, но разрешен доступ к IP-адресам Cloudflare CDN (так как через Cloudflare работают тысячи легитимных сайтов):

1. **Архитектура:**
   - Клиент отправляет трафик на публичный Anycast IP Cloudflare (который доступен в РФ).
   - В TLS ClientHello указывается разрешенный домен (Domain Fronting / CDN Proxying).
   - Внутри TLS-туннеля передается WebSocket или gRPC сессия.
   - Cloudflare CDN принимает сессию и по внутренней сети проксирует ее на ваш зарубежный сервер-источник (Origin VPS).
2. **Преимущество:** ТСПУ видит соединение исключительно с легитимным IP-адресом Cloudflare CDN с легальным SNI.
3. **Недостаток:** Более высокий RTT и ограничение скорости со стороны бесплатного тарифа Cloudflare (возможный троттлинг тяжелого трафика).

### 4.4. ShadowTLS v3 поверх легитимного TLS к белосписочному серверу

**ShadowTLS (версия 3)** — это специализированный криптографический протокол маскировки, разработанный специально для работы в условиях жестких белых списков.

#### Принцип работы ShadowTLS v3:
1. Клиент устанавливает реальное TCP-соединение с вашим прокси-сервером.
2. Клиент начинает стандартное TLS 1.3 рукопожатие.
3. Сервер ShadowTLS пересылает эти пакеты на настоящий доверенный веб-сайт из белого списка (Handshake SNI, например, `www.microsoft.com`).
4. На этапе завершения хэндшейка клиент отправляет специальный криптографический HMAC-токен, вычисленный на основе общего пароля.
5. Сервер проверяет HMAC:
   - Если хэндшейк отправлен сенсором ТСПУ — соединение навсегда передается настоящему серверу Microsoft.
   - Если хэндшейк содержит валидный HMAC — сервер незаметно для внешнего наблюдателя переключает сокет на внутренний прокси (Shadowsocks-2022).

### 4.5. Двухуровневая архитектура (Relay / Multi-hop / Внутрироссийский шлюз)

Когда трансграничные каналы связи фильтруются с максимальной агрессивностью, наиболее отказоустойчивой конфигурацией становится **двухуровневый каскад (Relay-схема)**:

```
┌─────────────────┐       ┌──────────────────────┐       ┌─────────────────────┐
│  Клиент в РФ    │ =====►│  RU VPS (Transit)    │ =====►│ Exit VPS (Зарубеж)  │ =====► Internet / AI
│  (Домашний ПК / │ Внутри│  Selectel / Timeweb  │ Транс-│ Hetzner / OVH       │        (WARP Out)
│   Смартфон)     │ РФ    │  (Москва / СПб)      │ граница│ (Германия / Финл.) │
└─────────────────┘       └──────────────────────┘       └─────────────────────┘
```

#### Механизм функционирования:
1. **Первый сегмент (Клиент -> Внутрироссийский VPS):**
   - Трафик идет исключительно внутри Рунета (AS оператора -> AS Selectel/Timeweb).
   - Трафик не пересекает трансграничные ТСПУ, поэтому любые проверки внешних белых списков на него не распространяются.
   - Для маскировки можно использовать легкий Shadowsocks-2022 или WireGuard.
2. **Второй сегмент (Внутрироссийский VPS -> Зарубежный VPS):**
   - Узел в РФ имеет корпоративный статический IP-адрес датацентра с высоким доверием.
   - Соединение между RU VPS и зарубежным Exit VPS устанавливается по протоколу VLESS-Reality с агрессивным тюнингом MTU и BBR.
3. **Третий сегмент (Exit VPS):**
   - Разделяет трафик: запросы к ИИ уходят в Cloudflare WARP, остальной трафик — напрямую в глобальный интернет.

### 5.3. Автоматизированный Python-скрипт генерации Cloudflare WARP WireGuard-конфигурации

Для автоматического получения учетных данных WireGuard WARP без использования сторонних бинарников написан легковесный Python-скрипт, использующий только стандартную библиотеку `urllib` и модуль `cryptography` (или генератор ключей WireGuard):

```python
#!/usr/bin/env python3
"""
Генератор учетных данных Cloudflare WARP для Sing-box WireGuard Outbound.
Создает пару ключей X25519, регистрирует аккаунт в API Cloudflare и
формирует готовый JSON-блок outbound для вставки в config.json sing-box.
"""

import urllib.request
import json
import base64
import os
import subprocess
from datetime import datetime, timezone

def generate_wireguard_keypair():
    """Генерация приватного и публичного ключей WireGuard через wg или openssl."""
    try:
        privkey_bytes = subprocess.check_output(["wg", "genkey"]).strip()
        pubkey_bytes = subprocess.check_output(["wg", "pubkey"], input=privkey_bytes).strip()
        return privkey_bytes.decode('utf-8'), pubkey_bytes.decode('utf-8')
    except Exception:
        # Fallback: генерация 32 случайных байт с правильным clamp для Curve25519
        import secrets
        key = bytearray(secrets.token_bytes(32))
        key[0] &= 248
        key[31] &= 127
        key[31] |= 64
        priv_b64 = base64.b64encode(key).decode('utf-8')
        # Для точного вычисления публичного ключа Curve25519 рекомендуется наличие утилиты wg
        # В большинстве Linux систем wg доступен через wireguard-tools
        return priv_b64, None

def register_warp(public_key: str):
    """Регистрация клиента в Cloudflare WARP REST API v0a2158."""
    url = "https://api.cloudflareclient.com/v0a2158/reg"
    headers = {
        "User-Agent": "okhttp/3.12.1",
        "Content-Type": "application/json; charset=UTF-8"
    }
    
    payload = {
        "install_id": "",
        "tos": datetime.now(timezone.utc).isoformat().replace("+00:00", "Z"),
        "key": public_key,
        "fcm_token": "",
        "type": "Android",
        "locale": "en_US"
    }
    
    req = urllib.request.Request(url, data=json.dumps(payload).encode('utf-8'), headers=headers, method="POST")
    with urllib.request.urlopen(req, timeout=15) as resp:
        return json.loads(resp.read().decode('utf-8'))

def main():
    print("[*] Генерация криптографических ключей WireGuard...")
    try:
        priv_key, pub_key = generate_wireguard_keypair()
    except Exception as e:
        print(f"[!] Ошибка генерации ключей: {e}")
        return

    if not pub_key:
        print("[!] Требуется утилита 'wg' из пакета wireguard-tools для вычисления публичного ключа.")
        return

    print(f"[+] Private Key: {priv_key}")
    print(f"[+] Public Key:  {pub_key}")
    print("[*] Отправка регистрационного запроса в Cloudflare Client API...")
    
    try:
        data = register_warp(pub_key)
    except Exception as e:
        print(f"[!] Ошибка подключения к API Cloudflare: {e}")
        return

    config = data.get("result", data).get("config", {})
    client_id = config.get("client_id", {})
    
    # Извлечение 3-байтового reserved массива
    reserved_raw = None
    if isinstance(client_id, str):
        reserved_bytes = base64.b64decode(client_id)
        reserved_raw = list(reserved_bytes)
    elif isinstance(client_id, list):
        reserved_raw = client_id
    elif isinstance(client_id, dict) and "reserved" in client_id:
        reserved_raw = client_id["reserved"]
    else:
        reserved_raw = [0, 0, 0]

    addresses = config.get("interface", {}).get("addresses", {})
    v4 = addresses.get("v4", "172.16.0.2/32")
    v6 = addresses.get("v6", "2606:4700:110:8fbb:bdf2:a2f6:a188:94d6/128")
    peer_pub = config.get("peers", [{}])[0].get("public_key", "bmXOC+F1FxEMF9dyiK2H5/1SUtzH0JuVo51h2wPfgyo=")
    endpoint = config.get("peers", [{}])[0].get("endpoint", {}).get("host", "162.159.192.1:2408")

    host, port = endpoint.split(":")

    singbox_warp_outbound = {
        "type": "wireguard",
        "tag": "warp-out",
        "server": host,
        "server_port": int(port),
        "local_address": [v4, v6],
        "private_key": priv_key,
        "peer_public_key": peer_pub,
        "reserved": reserved_raw,
        "mtu": 1280,
        "workers": 2
    }

    print("\n================ ГОТОВЫЙ БЛОК ДЛЯ SING-BOX CONFIG.JSON ================\n")
    print(json.dumps(singbox_warp_outbound, indent=2))
    print("\n=======================================================================\n")

if __name__ == "__main__":
    main()
```
