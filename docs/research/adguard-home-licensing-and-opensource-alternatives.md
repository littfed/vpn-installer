#### Ключевые отличия между AdGuard Home и клиентскими приложениями AdGuard Apps:
1. **Уровень фильтрации:**
   - **AdGuard Home** работает исключительно на уровне DNS (L7 протокол прикладного уровня разрешения имен). Он оперирует исключительно доменными именами (FQDN) и возвращает клиенту адрес `0.0.0.0` (NXDOMAIN / Custom IP) при попытке резолва рекламного или трекерного хоста. AdGuard Home **не может** вырезать рекламные баннеры внутри веб-страниц (HTML DOM), удалять пустые блоки или блокировать рекламу на YouTube, отдающуюся с тех же CDN-доменов, что и легитимный контент.
   - **AdGuard Apps (Windows/macOS/Android)** осуществляют локальный MITM (Man-in-the-Middle) HTTPS-трафика с генерацией пользовательского корневого сертификата, анализируют поток HTTP-данных, вырезают HTML-теги, выполняют инъекции косметических CSS/JS-скриптов и фильтруют URL на уровне путей запросов (`example.com/ads/*`).
2. **Юридический аспект:**
   - AdGuard Apps требуют приобретения лицензионного ключа (за исключением триального периода или ограниченных мобильных режимов).
   - AdGuard Home никогда не требует ключей, не имеет механизма проверки лицензий и является автономным проектом сообщества.

### 1.3. Телеметрия, политика приватности и проверяемость исходного кода (Auditability)

В контексте развертывания серверов обхода цензуры и защиты приватности критически важен вопрос отсутствия скрытой телеметрии в сторону вендора:

1. **Проверка обновлений (Update Checks):**
   - По умолчанию AdGuard Home периодически выполняет HTTP GET запрос к `https://static.adguard.com` для проверки наличия свежей версии бинарного файла и обновлений встроенных списков фильтрации.
   - Данное поведение полностью отключается в конфигурационном файле `AdGuardHome.yaml` параметром:
     ```yaml
     check_update: false
     ```
2. **Отсутствие сбора DNS-запросов:**
   - Исходный код AdGuard Home не содержит механизмов отправки DNS-логов пользователя разработчикам. Все запросы, IP-адреса клиентов и домены обрабатываются строго локально на инстансе.
   - Логи запросов (`querylog`) сохраняются в локальный файл `data/querylog.json` либо хранятся исключительно в оперативной памяти (в зависимости от настроек `querylog_interval` и `querylog_mem_size`).
3. **Аудируемость (Auditability):**
   - Поскольку весь стек написан на Go и не использует бинарных проприетарных блобов, сборка бинарного файла может быть полностью воспроизведена из исходного кода (`go build` / `make`) с верификацией контрольных сумм.
   - Сборка фронтенда находится в директории `client/` репозитория и компилируется стандартными инструментами `npm run build` без закрытых внешних компонентов.

### 2.2. Нативная реализация криптографических протоколов (DoH, DoT, DoQ, DoH3, DNSCrypt)

В отличие от многих конкурирующих решений (таких как Pi-hole или dnsmasq), которые способны принимать только открытый UDP/TCP 53 трафик и требуют внешних реверс-прокси (Caddy, Nginx, cloudflared) для шифрования, **AdGuard Home содержит полностью нативную серверную и клиентскую реализацию всех современных стандартов защищенного DNS**:

1. **DNS-over-TLS (DoT, RFC 7858):**
   - Нативно слушает порт `853/TCP`.
   - Поддерживает TLS 1.2 и TLS 1.3 с современными наборами шифров (AEAD: ChaCha20-Poly1305, AES-128-GCM, AES-256-GCM).
   - Предоставляет встроенную изоляцию клиентских сессий и TLS Session Resumption.
2. **DNS-over-HTTPS (DoH, RFC 8484):**
   - Нативно слушает порт `443/TCP`.
   - Поддерживает HTTP/1.1 и HTTP/2 (h2).
   - Реализует стандартный эндпоинт `/dns-query` (совместим с любыми ОС: Windows 11, iOS, Android Private DNS, macOS, браузерами Chrome/Firefox).
   - Поддерживает **Client Identification via URL path**: возможность отдавать различные политики фильтрации разным устройствам путем указания уникального URL, например `https://dns.example.com/dns-query/alice` или `https://dns.example.com/dns-query/kids`.
3. **DNS-over-QUIC (DoQ, RFC 9250):**
   - Нативно слушает порт `853/UDP` (ранее поддерживались драфт-порты `784/UDP`).
   - Построен на базе библиотеки `quic-go`. Обеспечивает нулевую задержку соединения (0-RTT), устраняет проблему Head-of-Line Blocking на уровне сетевых потерь пакетов, идеален для мобильных сетей со сменой IP-адресов.
4. **DNS-over-HTTP/3 (DoH3, RFC 9114):**
   - Нативно слушает порт `443/UDP`.
   - Инкапсулирует HTTP/3 запросы поверх протокола QUIC.
5. **DNSCrypt v2:**
   - Поддерживает протокол DNSCrypt как в роли сервера, так и в роли апстрим-клиента, обеспечивая криптографическую аутентификацию с эллиптическими кривыми (X25519).
6. **Автоматический выпуск и пролонгация сертификатов ACME (Let's Encrypt):**
   - В ядро AdGuard Home встроен собственный ACME-клиент. Прямо через веб-панель администратор может указать доменное имя, адрес электронной почты, и демон самостоятельно пройдет валидацию TLS-ALPN-01 или DNS-01, выпустит сертификат Let's Encrypt и настроит DoH/DoT/DoQ без сторонних утилит (certbot / acme.sh).

### 2.3. Движок правил фильтрации: Adblock Plus, hosts-файлы, регулярные выражения, модификаторы

Движок сопоставления правил AdGuard Home является одним из наиболее функциональных среди автономных DNS-серверов:

1. **Синтаксис базового сопоставления (Adblock-style):**
   - `||example.org^` — блокирует домен `example.org` и все его поддомены (`sub.example.org`, `tracker.sub.example.org`).
   - `@@||example.org^` — правило исключения (белый список), отменяет блокировку указанного домена.
2. **Модификаторы правил:**
   - `$important` — присваивает правилу наивысший приоритет (перекрывает любые белые списки).
   - `$badfilter` — отключает действие ранее загруженного правила из внешнего публичного списка.
   - `$dnsrewrite=1.2.3.4` или `$dnsrewrite=NOERROR;A;1.2.3.4` — мощный механизм переопределения DNS-ответов (DNS Spoofing / Local Overrides), позволяющий использовать AdGuard Home как локальный Split-Horizon DNS.
   - `$dnstype=AAAA` — применяет фильтрацию только к указанному типу DNS-записей (например, блокировка IPv6 AAAA-ответов для форсирования IPv4-маршрута).
   - `$client=192.168.1.50` или `$client='alice-phone'` — таргетированная фильтрация: правило применяется только к указанному IP-адресу или идентификатору клиента.
3. **Регулярные выражения (Regular Expressions):**
   - Поддержка синтаксиса `/^ad([0-9]+)?\..*$/` для комплексного сопоставления сгенерированных рекламных доменных имен через Go regexp engine.
4. **Совместимость с классическими форматами:**
   - Полная поддержка форматов `/etc/hosts` (`127.0.0.1 badsite.com`, `0.0.0.0 tracker.com`).
   - Прямой импорт форматов списков Pi-hole, Steven Black Hosts, OISD, AdGuard DNS filter, EasyList.

### 3.1. Pi-hole (FTLDNS / dnsmasq fork, EUPL v1.2 / GPLv2)

- **Первичные источники:**
  - Ядро FTL: [github.com/pi-hole/FTL](https://github.com/pi-hole/FTL)
  - Скрипты и окружение: [github.com/pi-hole/pi-hole](https://github.com/pi-hole/pi-hole)
  - Лицензия ядра FTL: **EUPL v1.2** (European Union Public Licence); скрипты: **GNU GPLv2**.
- **Архитектура:**
  - Ядро `pihole-FTL` написано на языке **C**. Исторически FTL является глубоко модифицированным форком легковесного демона `dnsmasq`.
  - Для долговременного хранения статистики, списков доменов и логов запросов используется СУБД **SQLite3** (`gravity.db` и `pihole-FTL.db`).
  - Классический веб-интерфейс AdminLTE до версии Pi-hole v5 требует связки из веб-сервера `lighttpd` и интерпретатора `PHP` (в разрабатываемой ветке Pi-hole v6 веб-сервер переписан на C и интегрирован внутрь бинарника FTL).
- **Механизм блокировки:**
  - Скачивает списки хостов и компилирует их в базу данных *Gravity*.
  - Поддерживает стандартные списки блокировок (HOSTS-формат) и сопоставление по регулярным выражениям (regex).
- **Критическое архитектурное ограничение для VPN/VPS:**
  - **В Pi-hole отсутствует нативная серверная поддержка протоколов DoH, DoT, DoQ и DoH3.**
  - `pihole-FTL` слушает исключительно стандартные сокеты `53/UDP` и `53/TCP`.
  - Чтобы подключить клиентское устройство (смартфон или Sing-box клиент) к Pi-hole по защищенному каналу DoH/DoT, администратор **обязан** разворачивать дополнительный проксирующий стек-сайдкар:
    - Связку `cloudflared` или `stubby` для апстрим-шифрования;
    - Веб-сервер `Caddy`, `Nginx` или `traefik` с самодельным маппингом HTTP-запросов `/dns-query` в локальный UDP-сокет `127.0.0.1:53`.
  - В Pi-hole отсутствует нативная поддержка синтаксиса правил Adblock Plus (модификаторы `$important`, `$badfilter`, `$dnsrewrite` работают иначе или требуют сторонних парсеров).

### 3.2. Blocky (Go, Apache 2.0, Headless, Container-Native)

- **Первичные источники:**
  - Репозиторий: [github.com/0xERR0R/blocky](https://github.com/0xERR0R/blocky)
  - Документация: [0xerr0r.github.io/blocky](https://0xerr0r.github.io/blocky/)
  - Лицензия: **Apache License 2.0**.
- **Архитектура:**
  - Написан на языке **Go**. Проект изначально задумывался как реакция на избыточную сложность Pi-hole для контейнеризированных окружений (Docker, Kubernetes).
  - **Headless-архитектура:** У Blocky полностью отсутствует встроенный Web UI. Вся конфигурация описывается декларативно в едином YAML-файле (`config.yml`).
  - **Container-Native & Cloud-Native:**
    - Нативно экспортирует богатые метрики в формате **Prometheus** (эндпоинт `:4000/metrics`) для визуализации в Grafana.
    - Поддерживает интеграцию с **Redis** для синхронизации кэша и состояния между несколькими географически распределенными инстансами (Multi-Instance High Availability).
- **Сетевые возможности:**
  - **Нативный DoH-сервер:** умеет принимать DoH-запросы напрямую при указании TLS-сертификата.
  - **Нативный DoT-сервер:** поддержка шифрованного TLS-транспорта для входящих соединений.
  - Поддержка условной маршрутизации запросов (Conditional Upstreams): разделение резолва доменов по группам клиентов и целевым зонам.
  - Синтаксис списков: загрузка списков из файлов и HTTP-источников, поддержка регулярных выражений.
- **Ресурсоемкость:**
  - Чрезвычайно низкое потребление памяти: от **15 до 30 МБ RAM**. Идеален для серверов с критическим дефицитом ресурсов.

### 3.3. Technitium DNS Server (C# / .NET, GPLv3, Authoritative + Recursive)

- **Первичные источники:**
  - Репозиторий: [github.com/TechnitiumSoftware/DnsServer](https://github.com/TechnitiumSoftware/DnsServer)
  - Портал: [technitium.com/dns](https://technitium.com/dns/)
  - Лицензия: **GNU General Public License v3.0 (GPLv3)**.
- **Архитектура:**
  - Написан на современном **C# (.NET 8 / .NET 9)**.
  - Представляет собой промышленный полнофункциональный DNS-сервер: совмещает функции **авторитетного (Authoritative)** сервера имен для собственных зон и **рекурсивного валидирующего резолвера (Recursive Resolver)**.
  - Полноценный встроенный адаптивный Web UI и исчерпывающий REST API для автоматизации управления записями зон.
  - **Модульная экосистема DNS Apps:** Встроенный магазин приложений, позволяющий в один клик устанавливать плагины:
    - *Advanced Blocking App* (блокировка рекламы, списки, маски);
    - *Split-Horizon / GeoDNS App*;
    - *Dynamic DNS App*;
    - *Query Log Exporters*.
- **Поддержка протоколов (максимальная в индустрии):**
  - Поддерживает **все** современные сетевые протоколы для входящих и исходящих соединений: UDP/TCP 53, **DNS-over-TLS (DoT)**, **DNS-over-HTTPS (DoH)**, **DNS-over-QUIC (DoQ)**, **DNS-over-HTTP/3 (DoH3)**, DNSCrypt.
  - Полная поддержка аппаратного и криптографического **DNSSEC** с авто-валидацией цепочек доверия.
- **Ограничения:**
  - Поскольку стек базируется на .NET Runtime, базовое потребление оперативной памяти составляет **150 – 350 МБ RAM**, что делает его тяжелее легковесных решений на C и Go на сверхдешевых VPS (хотя на серверах от 2 ГБ RAM это не имеет значения).

### 3.4. CoreDNS (Go, Apache 2.0, CNCF Graduated, Plugin Architecture)

- **Первичные источники:**
  - Репозиторий: [github.com/coredns/coredns](https://github.com/coredns/coredns)
  - Официальный сайт: [coredns.io](https://coredns.io/)
  - Лицензия: **Apache License 2.0** (Выпускник Cloud Native Computing Foundation — CNCF Graduated Project).
- **Архитектура:**
  - Написан на языке **Go**. Является стандартом де-факто для резолвинга сервисов внутри кластеров **Kubernetes**.
  - Архитектура построена на цепочке плагинов (*Plugin Chaining*). Каждый DNS-запрос последовательно проходит сквозь сконфигурированный конвейер плагинов, описанный в файле `Corefile`.
- **Возможности:**
  - Плагин `tls`: реализация входящего DoT сервера.
  - Плагин `https`: реализация входящего DoH сервера.
  - Сторонние плагины `blocklist` / `adblock`: позволяют блокировать домены по спискам.
  - Плагин `forward`: интеллектуальная пересылка запросов с балансировкой и health-check.
  - Плагин `prometheus`: нативный сбор метрик для телеметрии.
- **Ограничения:**
  - Отсутствует какой-либо графический веб-интерфейс (управление только через Corefile / ConfigMap).
  - В базовой поставке нет встроенного продвинутого парсера модификаторов Adblock Plus (требуется компиляция с нестандартными плагинами).

### 3.5. Unbound (C, BSD 3-Clause, NLnet Labs, Validating Recursive Resolver)

- **Первичные источники:**
  - Репозиторий: [github.com/NLnetLabs/unbound](https://github.com/NLnetLabs/unbound)
  - Документация: [nlnetlabs.nl/projects/unbound/about/](https://nlnetlabs.nl/projects/unbound/about/)
  - Лицензия: **BSD 3-Clause License**.
- **Архитектура:**
  - Написан на языке **C**. Разрабатывается нидерландским некоммерческим фондом NLnet Labs.
  - **Настоящий рекурсивный валидирующий резолвер:** В отличие от DNS-форвардеров (AdGuard Home, Pi-hole, Blocky), которым для работы требуется внешний апстрим (Cloudflare, Google, Quad9), Unbound способен опрашивать корневые DNS-серверы IANA напрямую:
    - Корневые серверы (`a.root-servers.net` ... `m.root-servers.net`) ➔ Серверы TLD (например, серверы зоны `.com`) ➔ Авторитетные серверы запрашиваемого домена (`ns1.example.com`).
  - **Максимальная приватность:** Ни один публичный резолвер (Google, Cloudflare) не видит историю ваших запросов.
  - **QNAME Minimization (RFC 7816 / RFC 9156):** Unbound отправляет вышестоящим авторитетным серверам строго необходимую часть домена (например, корневому серверу отправляется только запрос `com`, а не полный `secret.company.com`), предотвращая утечку метаданных на промежуточных узлах.
  - **Аппаратная валидация DNSSEC:** Жесткая криптографическая проверка подлинности записей, исключающая DNS Cache Poisoning.
- **Поддержка зашифрованных протоколов:**
  - Нативная поддержка DoT (как клиент и как сервер через `tls-service-key` и `tls-service-pem`).
  - Поддержка DoH-сервера (начиная с версий 1.13+ при сборке с `libnghttp2`).
- **Блокировка рекламы:**
  - Поддерживается через директивы `local-zone: "ad.example.com" always_null` или через механизм **RPZ (Response Policy Zones)**.
  - Конвертация списков блокировок требует внешних bash/python-скриптов.

### 3.6. PowerDNS Recursor (C++, GPLv2, Enterprise / ISP Scale, Lua Engine)

- **Первичные источники:**
  - Репозиторий: [github.com/PowerDNS/pdns](https://github.com/PowerDNS/pdns)
  - Документация: [doc.powerdns.com/recursor/](https://doc.powerdns.com/recursor/)
  - Лицензия: **GNU General Public License v2 (GPLv2)**.
- **Архитектура:**
  - Написан на языке **C++**. Промышленный рекурсивный резолвер операторского класса, используемый крупнейшими интернет-провайдерами (ISP) и телеком-корпорациями Европы и мира.
  - Рассчитан на колоссальные нагрузки: сотни тысяч QPS с поддержкой многопоточности и аппаратного сетевого ускорения.
  - **Встроенный Lua скриптинг:** Позволяет перехватывать и модифицировать любые DNS-пакеты на лету с использованием кода на языке Lua (Dynamic Policy Engine).
  - Поддержка **DNS Firewall (RPZ - Response Policy Zones)** для мгновенного импорта коммерческих баз фишинга и спама через DNS Zone Transfer (AXFR).
- **Специфика применения:**
  - Избыточен для персонального VPS или домашней сети. Требует глубоких знаний администрирования Linux и конфигурирования через текстовые файлы.

### 3.7. dnsmasq (C, GPLv2/GPLv3, Router / OpenWrt Standard)

  - Автор: Simon Kelley.

## 5. Рекомендации по выбору для vpn-installer и Self-Hosted стеков

### 5.1. Матрица принятия решений (Decision Matrix)

При проектировании архитектуры `vpn-installer` выбор DNS-бэкенда должен базироваться на конкретных системных ограничениях и требованиях к приватности:

```
Каковы ключевые требования к развертыванию DNS?
│
├── Нужен дружелюбный Web UI, статистика, управление черными/белыми списками в 1 клик,
│   нативный DoH/DoT/DoQ с автовыпуском Let's Encrypt и легкая установка на 1 VPS?
│   └──► ВЫБОР: ADGUARD HOME (Безусловный стандарт)
│
├── Сервер разворачивается строго в Headless / GitOps режиме (Docker Compose / Ansible / K8s),
│   память критически ограничена (<512 МБ), метрики нужны в Prometheus / Grafana?
│   └──► ВЫБОР: BLOCKY
│
├── Требуется нулевое доверие к третьим сторонам (Zero Trust to Upstream DNS),
│   защита от логирования запросов со стороны Cloudflare/Google, эталонная валидация DNSSEC?
│   └──► ВЫБОР: UNBOUND (либо связка ADGUARD HOME + UNBOUND)
│
└── Нужен полноценный авторитетный DNS-сервер со своей зоной, поддержкой DoQ/DoH3,
    DNSSEC и интеграцией с внутренними доменами компании?
    └──► ВЫБОР: TECHNITIUM DNS SERVER
```

---

### 5.2. Сценарий 1: Standalone All-in-One VPS (Sing-box + AdGuard Home)

**Почему AdGuard Home является лучшим выбором по умолчанию для `vpn-installer`:**
1. **Автономность и простота эксплуатации:** Один статический бинарник без системных зависимостей.
2. **Встроенный крипто-сервер:** Предоставляет нативные эндпоинты DoH (`https://vps.example.com/dns-query`) и DoT (`vps.example.com:853`), к которым могут безопасно подключаться мобильные клиенты (Android Private DNS, профили iOS DNS, клиенты Sing-box/AmneziaWG) без проброса открытого 53 UDP-порта наружу.
3. **Безопасность портов наружу:** Порт 53 UDP/TCP можно закрыть внешним фаерволом (`ufw` / `iptables`), оставив снаружи только защищенный TLS/QUIC транспорт, что полностью устраняет уязвимость к DNS Amplification DDoS-атакам.
4. **Управление переопределениями (DNS Rewrites):** Встроенный интерфейс позволяет в секунды добавить запись перенаправления для обхода гео-блокировок или развертывания внутреннего домена.

### 5.3. Сценарий 2: Минималистичный / GitOps стек (Sing-box + Blocky)

Если в архитектуре `vpn-installer` стоит цель полностью исключить веб-интерфейсы для минимизации поверхности атак и сократить потребление оперативной памяти до абсолютного минимума:

**Пример боевого `config.yml` для Blocky:**

### 5.4. Сценарий 3: Максимальная приватность и независимость (AdGuard Home + Unbound Local Resolver)

Для пользователей, стремящихся к бескомпромиссной приватности в условиях цензуры, рекомендуется связка **AdGuard Home (Frontend/Filter) + Unbound (Backend/Recursive Resolver)**.

```
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│                    ГИБРИДНАЯ АРХИТЕКТУРА: ADGUARD HOME + UNBOUND (LOCAL ROOT)                   │
└────────────────────────────────────────────────┬────────────────────────────────────────────────┘
                                                 │ Запрос клиента (DoH / DoT / VPN)
                                                 ▼
                             ┌──────────────────────────────────────┐
                             │       AdGuard Home (Frontend)        │
                             │  - Слушает DoH :443 / DoT :853       │
                             │  - Фильтрация рекламы и трекеров     │
                             │  - Веб-панель управления и логи     │
                             └───────────────────┬──────────────────┘
                                                 │ Апстрим: 127.0.0.1:5335 (Plain DNS)
                                                 ▼
                             ┌──────────────────────────────────────┐
                             │          Unbound (Backend)           │
                             │  - Слушает локальный порт 5335       │
                             │  - QNAME Minimization (RFC 9156)     │
                             │  - Прямой рекурсивный опрос Root DNS │
                             │  - DNSSEC аппаратная валидация       │
                             └───────────────────┬──────────────────┘
                                                 │
                   ┌─────────────────────────────┼─────────────────────────────┐
                   │ Опрос Root серверов         │ Опрос TLD серверов          │ Опрос SLD серверов
                   ▼                             ▼                             ▼
        ┌─────────────────────┐       ┌─────────────────────┐       ┌─────────────────────┐
        │  [a-m].root-servers │       │    .com / .org / .ru│       │   ns1.example.com   │
        └─────────────────────┘       └─────────────────────┘       └─────────────────────┘
```

1. **AdGuard Home** принимает зашифрованные запросы от клиентов VPN (Sing-box, WireGuard), применяет правила блокировки рекламы и кэширует популярные запросы.
2. В качестве единственного апстрима в AdGuard Home задается адрес:
   ```text
   127.0.0.1:5335
   ```
3. **Unbound**, запущенный на порту `5335`, выполняет итеративный опрос корневых серверов интернета с включенной минимизацией QNAME (`qname-minimisation: yes`), гарантируя, что ни Cloudflare, ни Google, ни провайдер VPS не получают метаданных о посещаемых ресурсах.

### 5.5. Архитектурная интеграция с Sing-box и AmneziaWG

В стеке `vpn-installer` локальный DNS интегрируется с VPN-клиентами следующим образом:

1. **Для AmneziaWG / WireGuard:**
   - В интерфейсе интерфейса сервера (`awg0` / `wg0`) в директиве `DNS` клиентского профиля задается внутренний IP адрес VPN-шлюза:
     ```ini
     [Interface]
     PrivateKey = <Client_Private_Key>
     Address = 10.8.0.2/24
     # Перенаправление DNS-запросов клиентов на AdGuard Home, слушающий интерфейс awg0
     DNS = 10.8.0.1
     ```
2. **Для Sing-box (Split-DNS с выборочной фильтрацией):**
   - На стороне сервера Sing-box объявляет локальный DNS-инбаунд либо перенаправляет трафик через правило маршрутизации на AdGuard Home:
     ```json
     {
       "dns": {
         "servers": [
           {
             "tag": "dns-adguard",
             "address": "tcp://127.0.0.1:53",
             "detour": "direct"
           }
         ],
         "rules": [
           {
             "outbound": "any",
             "server": "dns-adguard"
           }
         ]
       }
     }
     ```
