## 2. Архитектура и актуальное состояние цензуры ТСПУ в РФ (2025–2026 гг.)

### 2.1. Принципы работы и топология ТСПУ (DPI РКН)

В рамках закона «о суверенном Рунете» (ФЗ № 90-ФЗ) на сетях всех операторов связи РФ, имеющих автономный номер (ASN), установлены программно-аппаратные комплексы **ТСПУ (Технические средства противодействия угрозам)**. На 2025–2026 гг. инфраструктура охватывает свыше 99% абонентского интернет-трафика РФ.

```
       [Абонент в РФ]
             |
             v
     [Узел доступа ISP]
             |
   +---------+---------+
   |    L2 Bypass      |  <-- Режим "Bump-in-the-wire"
   |  (Bypass Switch)  |      (пропуск трафика на аппаратном уровне)
   +---------+---------+
             | (In-line)
      [Сенсор ТСПУ]       <-- Централизованное управление ЦМУ ССОП (РКН)
             |                 - Анализ пакетов (L3-L7 DPI)
             |                 - Дроп (Drop / Blackhole)
             |                 - Инъекция TCP RST / ICMP Unreachable
             v
   [Магистральный канал]
             |
             v
     [Внешний Internet]
```

**Особенности работы сенсоров:**
1. **Топология In-line:** ТСПУ монтируются в разрыв оптоволоконных каналов (bump-in-the-wire) через оптические обходные переключатели (Bypass). В случае сбоя питания переключатель пассивно пропускает трафик напрямую (fail-open), предотвращая падение канала связи оператора.
2. **Анализ состояний (Stateful Flow Tracking):** Сенсоры отслеживают TCP-сессии и UDP-потоки (5-tuple: IP source, IP dest, Port source, Port dest, Protocol). Для подозрительных потоков глубина анализа составляет от первых 3–5 пакетов (хендшейк) до первых 16–64 КБ передаваемых данных.
3. **Централизация правил:** Конфигурация сенсоров синхронизируется в реальном времени из ЦМУ ССОП (Центр мониторинга и управления сетью связи общего пользования, структура ГРЧЦ/РКН). Политики фильтрации могут применяться точечно (по отдельным макрорегионам или конкретным мобильным операторам) или глобально по всей стране.

### 2.2. Блокировки по сигнатурам и протоколам

#### WireGuard
Классический протокол WireGuard (RFC / спецификация Джейсона Доненфельда) в РФ на магистральном уровне и сетях мобильных операторов заблокирован почти на 100%.

**Механизм детекции:**
- **Инициация рукопожатия (Handshake Initiation):** Фиксированный размер UDP-пакета ровно `148 байт`. Первый байт (Message Type) равен `0x01`, далее следуют три зарезервированных нулевых байта `0x00 0x00 0x00`, затем 32-байтный sender index, незашифрованный эфемерный ключ Curve25519, зашифрованный статический ключ и HMAC/Cookie (`Mac1`, `Mac2`).
- **Ответ рукопожатия (Handshake Response):** Фиксированный размер ровно `92 байта`, тип сообщения `0x02 0x00 0x00 0x00`.
- **Логика ТСПУ:** При обнаружении пары UDP-пакетов «148 байт -> зарубежный IP» и «92 байта <- ответ» ТСПУ мгновенно сбрасывает последующие транспортные пакеты (`Message Type 0x04`, размер 32 байта + payload) для данного 5-tuple. На мобильных сетях блокируется даже одиночный пакет 148 байт (дропается без доставки до сервера).

#### OpenVPN
- **UDP-транспорт:** Фиксированный заголовок первого пакета инициализации (`P_CONTROL_HARD_RESET_CLIENT_V2` = `0x38` или `_V3` = `0x40`). Размер пакета хендшейка с TLS ClientHello типичен.
- **TCP-транспорт:** Первые 2 байта содержат длину пакета в big-endian, за которыми следует опкод OpenVPN. ТСПУ детектирует эти байты в первом TCP сегменте и инжектирует TCP RST в сторону клиента и сервера.
- **Статус в РФ:** Блокируется гарантированно за 1–2 секунды после начала хендшейка. Включение встроенного TLS-Auth / TLS-Crypt не спасает, так как сами структуры заголовков и размеры пакетов остаются легко узнаваемыми.

#### Классический Shadowsocks (SS-AEAD: chacha20-ietf-poly1305, aes-256-gcm)
- **Проблема «Random Noise» / Энтропия:** Трафик Shadowsocks не имеет открытых заголовков и выглядит как абсолютно случайные псевдослучайные байты с высокой энтропией Шеннона ($H \approx 8.0$).
- **Активное зондирование (Active Probing):** ТСПУ при обнаружении неизвестного входящего TCP-соединения с высокой энтропией отправляет на целевой IP и порт зондирующие запросы (повтор пакетов, измененные байты, псевдо-TLS хендшейки). Старый Shadowsocks при получении некорректных данных молча разрывал соединение (RST) или держал сокет открытым без ответа. Этот профиль поведения позволял мгновенно подтверждать наличие прокси и заносить IP в черный список.
- **Статус в РФ:** Заблокирован на мобильных операторах и многих ШПД-провайдерах, особенно при трафике на популярные зарубежные хостинги (Hetzner, OVH, DigitalOcean).

#### IPsec (IKEv1 / IKEv2), OpenConnect / AnyConnect
- **IKEv2:** UDP порты 500 и 4500, фиксированный формат заголовка ISAKMP (Initiator SPI, Responder SPI = 0, Next Payload, Version `0x20`). Блокируется фильтром по портам и сигнатурам.
- **ESP (IP protocol 50):** Блокируется на уровне L3 у большинства провайдеров РФ при транзите через государственную границу.
- **OpenConnect (Cisco AnyConnect / ocserv):** Хотя использует TLS поверх TCP, в первом запросе передаются специфические HTTP-заголовки (`X-AnyConnect-Platform`, `X-CSTP-Address`), которые перехватываются DPI.

### 2.3. Анализ и фильтрация TLS-отпечатков

В 2024–2026 гг. ТСПУ перешли от анализа L4 к продвинутому анализу L7 TLS ClientHello:

```
+-------------------------------------------------------------------------+
|                        TLS 1.3 ClientHello                              |
+-------------------------------------------------------------------------+
| - Record Layer (0x16 0x03 0x01 ...)                                     |
| - Handshake Protocol (ClientHello: 0x01)                                |
| - Version (0x0303 - TLS 1.2 compatibility)                              |
| - Random (32 bytes)                                                     |
| - Session ID                                                            |
| - Cipher Suites (набор и ПОРЯДОК следования шифров)                     |
| - Compression Methods                                                   |
| - Extensions:                                                           |
|     * server_name (SNI)                                                 |
|     * supported_groups (elliptic curves)                                |
|     * signature_algorithms                                              |
|     * supported_versions (0x0304 - TLS 1.3)                             |
|     * key_share                                                         |
|     * application_layer_protocol_negotiation (ALPN: h2, http/1.1)       |
+-------------------------------------------------------------------------+
```

1. **Детекция JA3 / JA4 отпечатков:**
   - Хеш **JA3** строится по формуле: `SSLVersion,CipherSuites,Extensions,EllipticCurves,EllipticCurvePointFormats` (MD5).
   - Хеш **JA4** расширяет этот подход, учитывая протокол (TCP/QUIC), число cipher suites, наличие SNI, алфавитный порядок расширений и сигнатурных алгоритмов.
   - **Практика ТСПУ:** Программы обхода на чистом Go (стандартный `crypto/tls`) или Python без маскировки формируют характерный для данных библиотек ClientHello. ТСПУ сравнивает отпечаток: если заголовок User-Agent или трафик эмулирует браузер Chrome, но TLS-хендшейк имеет отпечаток Go-рантайма, сессия сбрасывается.
2. **Блокировка ECH (Encrypted Client Hello):**
   - ECH призван скрыть SNI за счет шифрования внутреннего ClientHello публичным ключом из DoH/DNS HTTPS-записи.
   - Осенью 2024 года РКН начал массовую блокировку ECH в РФ. ТСПУ анализирует расширение `encrypted_client_hello` (`0xfe0d`) в открытом внешнем ClientHello: если пакет содержит это расширение, соединение сбрасывается или не пропускается дальше первого пакета. Это сделало использование Cloudflare ECH невозможным для пользователей внутри РФ.
3. **Фильтрация по SNI (Server Name Indication):**
   - ТСПУ проверяет поле SNI в открытом виде. Если домен числится в реестре запрещенных сайтов (ЕАИС), генерируется сброс (TCP RST) или внедряется фиктивный HTTP 302/поддельный сертификат заглушки.
   - **SNI Whitelisting (Режим «белых списков»):** При введении локальных режимов ЧС или тестировании изоляции сенсоры отбрасывают все соединения с SNI, которых нет в предварительно одобренном государственном списке доверенных ресурсов (.ru, .рф, порталы госуслуг, банковские шлюзы).

### 2.4. Блокировки и деградация (троттлинг) UDP / QUIC / HTTP/3

UDP-трафик в РФ подвергается жесткой дискриминации:

1. **Блокировка QUIC / HTTP/3 (порты 443/UDP):**
   - ТСПУ детектирует начальные пакеты QUIC (Initial Packet: заголовок Long Header, фиксированный `Version = 0x00000001`, тип `0x00`).
   - На многих магистральных каналах и сетях операторов связи трафик QUIC к зарубежным серверам принудительно дропается или замедляется, заставляя браузеры откатываться (fallback) на TCP-стек (TLS 1.3 over TCP).
2. **Агрессивный троттлинг UDP (UDP Shaper):**
   - Операторы «Большой четверки» (МТС, МегаФон, Билайн, Т2) применяют шейпинг на неизвестный UDP-трафик за пределы РФ. При превышении порога в 1–3 Мбит/с на один сокет (5-tuple) потери пакетов искусственно увеличиваются до 40–80%, либо скорость срезается до 512–1024 Кбит/с.
3. **Полный блэкаут UDP:**
   - Во время массовых мероприятий или в приграничных регионах наблюдаются периоды полного отключения внешнего UDP-трафика (whitehole). Все протоколы, использующие исключительно UDP (WireGuard, классический QUIC), полностью перестают функционировать.

### 2.5. Сценарии «Белых списков» и автономного рунета

В рамках сценариев «автономного интернета» (учения РКН):
1. **Отзыв BGP-сессий с зарубежными IXP:** Имитация физического повреждения или отключения внешних трансграничных стыков.
2. **Default-Deny для внешнего трафика:** Пропуск только тех IP-адресов и SNI, которые внесены в национальный белый список (реестр доверенных сервисов Минцифры).
3. **Вывод для архитектуры обхода:** Решение должно поддерживать маскировку под критически важные домены белого списка (CDN, корпоративные шлюзы зарубежных сервисов, не попадающие под фильтры) и иметь возможность работать через проксирование поверх HTTP/HTTPS портов (443/TCP).

## 3. Глубокий технический анализ протоколов и транспортов

### 3.1. VLESS + XTLS Reality

На сегодняшний день связка **VLESS + XTLS Reality + Vision** является «золотым стандартом» противодействия ТСПУ в РФ.

```
+----------------------------------------------------------------------------------------+
|                               Схема работы XTLS Reality                                |
+----------------------------------------------------------------------------------------+

  [Клиент Reality]                                [Сервер VPS]                   [Целевой сайт]
         |                                              |                       (напр. apple.com)
         | --- 1. ClientHello (SNI: apple.com, -------> |                               |
         |        PublicKey в SessionID / AuthKey)      |                               |
         |                                         [Проверка ключа]                     |
         |                                         Успех? -> НАШ КЛИЕНТ                 |
         |                                                |                             |
         | <--- 2. ServerHello (сертификат apple.com) -+ |                             |
         |         (зашифрован ECDH x25519)            |                                |
         |                                             |                                |
         | === 3. VLESS Tunnel (данные внутри TLS) ===>| [Распаковка и Direct Out]      |
         |                                                                              |
  [DPI / Active Prober]                                                                 |
         | --- Неавторизованный ClientHello ----------> |                               |
         |                                         [Проверка ключа]                     |
         |                                         Ошибка! -> ЧУЖОЙ                     |
         |                                              | --- ProxyPass / Fallback ---> |
         | <--- Реальный сертификат и ответ сайта <------------------------------------+
```

#### Принцип работы и SNI-Stealing
- **Устранение собственного домена и сертификата:** Обычный Trojan/VLESS-TLS требует покупки домена и выпуска сертификата Let's Encrypt. Это уязвимо: домен легко вычислить через Certificate Transparency Logs, а новый/дешевый домен моментально привлекает внимание эвристик ТСПУ.
- **Подмена личности (SNI-Stealing):** Сервер Reality настраивается на прослушивание порта 443/TCP. В качестве маскировки указывается легитимный сторонний домен (Target Server Name, например, `swdist.apple.com` или `gateway.icloud.com`), поддерживающий TLS 1.3 и протокол HTTP/2.
- **Аутентификация через ECDH:**
  - На сервере генерируется ключевая пара X25519 (`PrivateKey` и `PublicKey`) и шестнадцатеричный `ShortId`.
  - При подключении авторизованный клиент формирует валидный TLS 1.3 ClientHello, в который зашивает свой эфемерный публичный ключ и ShortId в поля `Session ID` (или в расширения).
  - Сервер Reality, перехватив ClientHello, с помощью своего `PrivateKey` проверяет подлинность клиента.
  - Если проверка **успешна**: сервер не обращается к реальному сайту, а сам отвечает клиенту, шифруя данные сессии вычисленным общим секретом ECDH.
  - Если проверка **не удалась** (подключение сканера РКН, робота цензуры или случайного пользователя): сервер Reality прозрачно перенаправляет трафик (fallback) на реальный целевой IP-адрес маскировочного домена. Сканер получает 100% валидный оригинальный TLS-сертификат Apple/Microsoft и корректный HTTP-ответ веб-сервера.

#### Flow `xtls-rprx-vision`
Ключевая проблема любого туннеля поверх TLS — явление **TLS-in-TLS**:
Когда пользователь открывает сайт HTTPS через VPN-прокси, зашифрованный TLS-поток пользователя упаковывается внутрь внешнего TLS-потока прокси. Системы DPI анализируют распределение длин пакетов и находят вложенные записи ClientHello (`0x16 0x03 0x01`) внутри прикладных данных.

**Механизм Vision:**
1. **Inner Padding:** Динамическое дополнение пакетов случайным мусором на этапе рукопожатий внутреннего TLS, сглаживающее статистические паттерны длин пакетов.
2. **Direct Splice (Zero-Copy):** На уровне Linux-ядра после завершения внутреннего TLS-хендшейка прокси-сервер переключается в режим системного вызова `splice()`. Данные копируются напрямую между сокетами в пространстве ядра без промежуточных криптографических обёрток, что даёт колоссальный прирост скорости и снижает нагрузку на CPU до минимума.

#### Транспорт XHTTP (v2ray / Xray 2025)
В новейших версиях Xray появился транспорт **XHTTP** (ранее разрабатывавшийся как замена split-HTTP):
- Инкапсулирует прокси-трафик в стандартные HTTP/1.1, HTTP/2 или HTTP/3 запросы с потоковой передачей чанков.
- Позволяет трафику беспрепятственно проходить через жесткие WAF, корпоративные Forward-прокси и CDN (Cloudflare, Fastly), которые блокируют классические WebSocket и gRPC потоки.

#### Правила подбора SNI для Reality в юрисдикции РФ
Неправильный подбор SNI — главная причина деградации Reality. ТСПУ выявляет аномалии по следующим факторам:
1. **Топологическая близость (RTT Delta):**
   - Если ваш VPS находится во Франкфурте (пинг от Москвы ~45 мс), а выбранный SNI резолвится в сервер в Сингапуре (пинг от Франкфурта ~180 мс), DPI зафиксирует аномальную разницу между TCP-хендшейком (45 мс) и ответом TLS ServerHello.
   - **Правило:** Целевой домен должен резолвиться в IP-адрес того же автономного региона/ASN, что и ваш VPS (например, Hetzner, OVH, Leaseweb) или иметь серверы в том же городе.
2. **Требование к протоколам:** Целевой сервер **обязан** поддерживать **TLS 1.3** и ALPN **h2** (HTTP/2). Если сервер отдает только TLS 1.2, Reality не сможет корректно работать.
3. **Отсутствие блокировки в РФ:** SNI-домен не должен быть внесен в реестры РКН, иначе само обращение к нему повлечет сброс соединения на ТСПУ еще до достижения VPS.
4. **Запрет на Cloudflare CDN IP:** Домены, сидящие за Cloudflare, не рекомендуются, так как ТСПУ активно тестирует адресные блокировки подсетей Cloudflare и фильтрует их сертификаты.

### 3.2. AmneziaWG (AWG)

AmneziaWG — глубокая модификация ядра WireGuard, созданная разработчиками проекта Amnezia VPN специально для преодоления ТСПУ в РФ.

```
Классический WireGuard:
[Type: 1B (0x01)] [Reserved: 3B (0x00)] [Sender Index: 4B] [Unhashed Ephemeral: 32B] ...
---> Фиксированная длина: ровно 148 байт (ДЕТЕКТ ТСПУ)

AmneziaWG:
[Junk Packet 1: Jmin..Jmax байт случайных данных]
[Junk Packet 2: Jmin..Jmax байт случайных данных]
... (всего Jc пакетов)
[Handshake Init: H1 (4B)] [Sender Index] ... [Случайный Padding S1 байт]
---> Переменный размер: 148 + S1 байт, тип сообщения изменен на H1
```

#### Эволюция версий AmneziaWG
1. **AWG 1.0 – 1.5:** Введение статических параметров `H1–H4` (замена байтов типа), `S1–S2` (паддинг хендшейков), `Jc` (число мусорных пакетов), `Jmin`/`Jmax` (размер мусорных пакетов).
2. **AWG 2.0:** Введение диапазонов для динамических заголовков и служебных сигнатурных пакетов (`I1–I5`), эмулирующих легитимные прикладные протоколы (DNS, NTP, STUN).
3. **AWG 3.1 (Header Protection):** Полное шифрование служебных открытых заголовков с помощью ChaCha20, предотвращающее эвристический анализ ТСПУ на основе статичных хешей.

#### Механика ключевых параметров:
- **`Jc` (Junk Packet Count):** Количество мусорных UDP-пакетов, генерируемых клиентом перед отправкой настоящего рукопожатия (рекомендуется от `3` до `8`). ТСПУ ожидает немедленного рукопожатия; мусорные пакеты сбивают конечный автомат DPI.
- **`Jmin` / `Jmax`:** Минимальный и максимальный размер мусорного пакета (например, `Jmin = 40`, `Jmax = 300` байт). Размывают спектрограмму распределения длин пакетов.
- **`S1` / `S2` (Init & Response Padding):** Добавочный случайный размер к стандартным пакетам инициализации (148 байт) и ответа (92 байта). Размер реального пакета становится `148 + S1` и `92 + S2`, разрушая правило сигнатурного детектора.
- **`H1`, `H2`, `H3`, `H4`:** Произвольные 32-битные целые числа (в диапазоне от 1 до 4294967295), заменяющие константы WireGuard:
  - `H1` заменяет `0x01` (Handshake Initiation)
  - `H2` заменяет `0x02` (Handshake Response)
  - `H3` заменяет `0x03` (Cookie Reply)
  - `H4` заменяет `0x04` (Transport Data)

#### Уязвимости и ограничения AWG:
- **Отсутствие маскировки под стандартный прикладной L7-трафик:** Трафик AWG после хендшейка представляет собой непрерывный поток UDP-пакетов высокой энтропии без структуры TLS или DTLS.
- **Уязвимость к эвристикам ТСПУ:** Если ТСПУ на сети оператора включает эвристику «блокировать неизвестный долгоживущий UDP-поток за рубеж с непрерывным обменом данными», сессия AWG деградирует через несколько сотен мегабайт переданных данных.
- **Неустойчивость при блэкауте UDP:** При отключении UDP оператором протокол полностью недееспособен.

### 3.3. Hysteria 2

**Hysteria 2** — протокол на базе глубоко модифицированного стека QUIC, ориентированный на максимальную скорость и преодоление неблагоприятных сетевых условий (высокие потери, троттлинг, нестабильные мобильные каналы).

#### Архитектура и алгоритм контроля перегрузок Brutal CC
Классические алгоритмы TCP (Cubic, Reno) и даже BBR трактуют потерю пакетов (packet loss) как признак перегрузки сети и немедленно снижают скорость отправки (`cwnd`). На мобильных сетях в РФ потери часто обусловлены не перегрузкой, а плохим покрытием радиосети или искусственным дропом на ТСПУ.

- **Brutal Congestion Control:**
  - Клиент и сервер явно договариваются о целевой пропускной способности (например, `100 Mbps Down / 30 Mbps Up`).
  - Алгоритм **фиксирует скорость отправки пакетов на заданном уровне**, полностью игнорируя потери пакетов (loss-agnostic).
  - Если на линии наблюдается потеря 25% пакетов, стандартный TCP падает по скорости в 10–20 раз; Hysteria 2 просто агрессивно досылает потерянные фрагменты на максимальной скорости, утилизируя 100% оставшейся физической емкости канала.

```
Скорость передачи при потерях пакетов (Loss Rate 20%):

TCP BBR / Cubic :  [===>                         ] ~ 2-5 Mbps
Hysteria 2 Brutal: [============================>] ~ 80 Mbps (целевая 100 Mbps)
```

#### Обфускация Salamander
Стандартный QUIC демаскирует себя заголовками пакетов (Fixed Bits, Packet Number, Connection ID). Чтобы скрыть QUIC от ТСПУ, в Hysteria 2 встроен протокол обфускации **Salamander**:
- Клиент и сервер используют общий секретный пароль.
- Каждый исходящий UDP-пакет подвергается побайтовому преобразованию на базе пароля и генератора псевдослучайных последовательностей.
- Пакеты теряют любую внутреннюю структуру, превращаясь в равномерный шум (indistinguishable from random noise). DPI не может распознать в них QUIC-хендшейк.

#### Механизм Port Hopping (Мультипортовый балансинг)
Чтобы обойти троттлинг по 5-tuple со стороны ТСПУ, Hysteria 2 поддерживает автоматический перебор портов:
- На сервере с помощью `iptables` открывается пул портов (например, `UDP 20000:50000 -> 443`).
- Клиент динамически с заданной периодичностью (или при росте задержек/потерь) переключает исходящий UDP-порт назначения. Для сенсора ТСПУ это выглядит как закрытие одной кратковременной сессии и открытие новой, не давая включиться шейперу долгоживущих потоков.

### 3.4. TUIC v5

**TUIC (Time-space Unified Internet Congestion-control)** — высокоскоростной протокол проксирования поверх чистого QUIC (реализован на Rust с использованием библиотеки `quinn`).

#### Особенности реализации v5:
1. **0-RTT Handshake:** За счет сохранения токенов сессий последующие соединения устанавливаются без задержки в RTT.
2. **Встроенное мультиплексирование:** Множественные TCP и UDP потоки заворачиваются в единую QUIC-сессию, что исключает эффект Head-of-Line Blocking на уровне отдельных TCP-соединений.
3. **Нативный UDP Relay:** Идеально подходит для передачи голосового трафика (Discord, Telegram calls) и онлайн-игр с минимальным оверхедом.
4. **Поведение в РФ:** Так как TUIC v5 использует стандартный QUIC без встроенной обфускации уровня Salamander, он сильнее уязвим к блокировкам по сигнатурам QUIC на сетях операторов связи РФ, чем Hysteria 2. Требует маскировки SNI и валидных сертификатов.

### 3.5. Shadowsocks-2022 и обфускаторы

#### Спецификация Shadowsocks-2022
В 2022 году протокол Shadowsocks был полностью переработан группой разработчиков для закрытия архитектурных уязвимостей классического SS:
- **Раздельное шифрование заголовков:** Заголовок каждого пакета имеет собственный AEAD-тег, что делает невозможным подбор длины полезной нагрузки.
- **Встроенная защита от атак повторного воспроизведения (Replay Attacks):** Сессионный заголовок включает временную метку (timestamp) и скользящее окно идентификаторов пакетов. Зонды ТСПУ, повторяющие перехваченные пакеты, отбрасываются сервером мгновенно.
- **Поддержка методов:** `2022-blake3-aes-128-gcm`, `2022-blake3-aes-256-gcm`, `2022-blake3-chacha20-poly1305`.

#### Связка с ShadowTLS v3
ShadowTLS решает проблему детекции энтропии Shadowsocks за счет взаимодействия с реальным легитимным сервером:
- Клиент ShadowTLS инициирует настоящий TLS 1.3 хендшейк с выбранным внешним сайтом (например, `cloud.google.com`).
- Сервер ShadowTLS находится в роли посредника: он пропускает рукопожатие к реальному сайту до момента завершения TLS Handshake.
- После успешного завершения хендшейка клиент посылает специальный HMAC-токен, подтверждающий авторизацию, и сервер переключает поток на внутренний порт Shadowsocks-2022.
- **Плюс:** 100% аутентичный TLS-хендшейк.
- **Минус:** Требует запуска двух раздельных демонов (ShadowTLS + Shadowsocks), что усложняет мониторинг и настройку по сравнению с монолитным решением VLESS Reality в sing-box/Xray.

### 4.4. Стандарты доставки и синхронизации конфигураций (Subscription)

Для обеспечения непрерывного доступа конечных пользователей к серверам необходимо организовать автоматическую выдачу конфигураций:

1. **Единые URI-схемы (Share Links):**
   - **VLESS Reality:**
     ```
     vless://<UUID>@<IP-or-Domain>:443?encryption=none&security=reality&sni=<SNI-Domain>&fp=chrome&pbk=<PublicKey>&sid=<ShortId>&type=tcp&flow=xtls-rprx-vision#MyVPN-VLESS
     ```
   - **Hysteria 2:**
     ```
     hysteria2://<Password>@<IP-or-Domain>:443?insecure=0&sni=<SNI-Domain>&obfs=salamander&obfs-password=<ObfsPassword>#MyVPN-Hy2
     ```
   - **AmneziaWG (Conf File):**
     Текстовый файл формата WireGuard INI с дополнительными полями `Jc`, `Jmin`, `Jmax`, `S1`, `S2`, `H1`, `H2`, `H3`, `H4`.
2. **Base64 Subscription List:**
   HTTP-эндпоинт на сервере (например, `https://sub.myvpn.net/api/v1/sub/<token>`), возвращающий список URI-ссылок, закодированный в Base64. Поддерживается 99% клиентов (v2rayNG, Streisand, v2rayN, Shadowrocket).
3. **Нативные профили Sing-box JSON / Clash Meta YAML:**
   Динамическая генерация единого файла конфигурации по запросу клиента с определением `User-Agent`. Если запрос идет от клиента sing-box — сервер отдает полный JSON со всеми outbounds и DNS-маршрутизацией.

| **Устойчивость к UDP-троттлингу** | **Иммунитет** (работает по TCP) | **Уязвим** (падает при шейпинге UDP) | **Высокая** (Brutal CC + Port Hopping) | **Иммунитет** (работает по TCP) | Уязвим |
| **Работа при блэкауте UDP** | **Работает штатно** | **Полный отказ** | **Полный отказ** | **Работает штатно** | Полный отказ |
| **Скорость на чистом канале** | До 10 Гбит/с (Splice) | До 1–2 Гбит/с | До 1–3 Гбит/с | До 1 Гбит/с | До 500 Мбит/с |
| **Поведение на мобильных сетях (потери 15–30%)** | Среднее (TCP head-of-line delay) | Хорошее | **Превосходное** (Brutal форсирует доставку) | Среднее | Критическое падение скорости |
| **Задержка (Latency / RTT)** | 1 RTT (TLS 1.3) | **0 RTT** (stateless crypto) | 0–1 RTT | 2 RTT (Double handshake) | 2–3 RTT |
| **Требования к серверу (CPU/RAM)** | Крайне низкие | Минимальные (в ядре) | Средние (CPU intensive при Brutal) | Средние (2 демона) | Низкие |
| **Простота настройки клиентом** | Сканирование QR / Ссылка | Импорт файла `.conf` | Сканирование QR / Ссылка | Сложная связка | Установка профиля |
| **Доступность бесплатных клиентов (iOS/Android/PC)** | **100%** (Streisand, v2rayNG, Hiddify) | **Ограниченно** (только Amnezia / Shadowrocket) | **90%** (Streisand, NekoBox, Hiddify) | **70%** (NekoBox, Shadowrocket) | 100% (но бессмысленно) |

## 6. Архитектурные рекомендации для `vpn-installer`

### 6.1. Рекомендуемый стек протоколов (Tier-1 + Fallback)

Для обеспечения 100% отказоустойчивости в условиях цензуры в РФ архитектура `vpn-installer` должна строиться на двухкомпонентном гибридном стеке:

```
                  +-------------------------------------------------+
                  |       Клиентское приложение (Hiddify/NekoBox)   |
                  +-------------------------------------------------+
                                     |
               +---------------------+---------------------+
               |                                           |
      (Основной канал / ТСПУ)                    (Мобильный / Потери пакетов)
               |                                           |
               v                                           v
   +-----------------------+                   +-----------------------+
   |   VLESS + Reality     |                   |  Hysteria 2 / AWG     |
   |   (TCP port 443)      |                   |  (UDP Port Hopping)   |
   |   - Неблокируемый     |                   |  - Пробив потерь      |
   |   - Zero-Copy Splice  |                   |  - Brutal CC          |
   |   - Полная маскировка |                   |  - Минимальный пинг   |
   +-----------------------+                   +-----------------------+
```

1. **Основной транспорт (Tier 1 - Default & Censorship-Proof):**
   - **VLESS + TCP + XTLS Reality + Vision** на порту `443/TCP`.
   - **Назначение:** Общий веб-серфинг, скачивание файлов, работа в условиях жестких блокировок, белых списков и принудительного отключения UDP оператором связи.
2. **Резервный / Мобильный акселератор (Tier 2 - Fallback & Gaming):**
   - **Hysteria 2** с обфускацией **Salamander** и пулом портов через `iptables` (Port Hopping: UDP 20000–50000 -> порт Hy2).
   - **Назначение:** Мобильные устройства при перемещении (автомобиль, поезд, метро), онлайн-игры, чувствительные к потерям и пингу, голосовая связь VoIP.
3. **Альтернативный L3-туннель (Tier 3 - Smart Home / Keenetic Routers):**
   - **AmneziaWG (AWG):** Для легкой интеграции на домашние роутеры (Keenetic, OpenWrt, Mikrotik) и устройства, где невозможно установить клиенты sing-box/Xray.

---

### 6.2. Архитектура сервисов (Docker / sing-box)

Рекомендуется строить серверную часть `vpn-installer` на базе единого демона **sing-box**, запускаемого в контейнере Docker:
- **Преимущество:** Единый бинарник sing-box закрывает входящие соединения VLESS Reality, Hysteria 2 и Shadowsocks-2022 одновременно, исключая конфликты портов и накладные расходы на поддержание разных служб.
- **Поддержка Docker Compose:** Обеспечивает изоляцию, быстрый деплой одной командой на любой Linux-дистрибутив (Debian 12, Ubuntu 22.04/24.04, AlmaLinux) и простоту обновлений.

```
       [Входящий трафик: 443/TCP, 443/UDP, 20000-50000/UDP]
                               |
                               v
                     +-------------------+
                     | Docker: sing-box  |
                     |  - Inbound VLESS  |
                     |  - Inbound Hy2    |
                     |  - DNS Handler    |
                     |  - Outbound Direct|
                     +-------------------+
                               |
                               v
               [Выход в открытый Интернет VPS]
```

### 6.3. Автоматизация генерации ключей и Reality SNI Scraper

Для работы VLESS Reality инсталлятор должен в автоматическом режиме выполнять:
1. **Генерацию ключей X25519:**
   ```bash
   sing-box generate reality-keypair
   # Возвращает:
   # Private key: <base64_encoded_x25519_private_key>
   # Public key:  <base64_encoded_x25519_public_key>
   ```
2. **Генерацию ShortId:**
   ```bash
   openssl rand -hex 8
   # Пример: e4a1b89c3f2d017a
   ```
3. **Генерацию UUID для пользователя:**
   ```bash
   sing-box generate uuid
   ```
4. **Алгоритм выбора и валидации SNI-домена (SNI Scraper):**
   Скрипт развертывания должен протестировать список кандидатов (например, `dl.google.com`, `swdist.apple.com`, `gateway.icloud.com`, `www.microsoft.com`, `s0.awsstatic.com`) по следующим критериям:
   - Поддержка TLS 1.3 (`openssl s_client -connect <IP>:443 -tls1_3`).
   - Поддержка ALPN HTTP/2 (`h2`).
   - Пинг / RTT от VPS до IP выбранного домена (должен быть $< 10$ мс, в идеале в пределах одной локации/ЦОД).
   - Проверка доступности домена из РФ (через публичные DoH-резолверы и проверку отсутствия в реестре РКН).
