## 1. Введение и постановка задачи

### 1.1. Переход от Single-Node к распределенному пулу (Fleet Architecture)

Классическая схема развертывания персонального или корпоративного VPN подразумевает установку всех сервисов на одном выделенном сервере (Virtual Private Server, VPS). Инсталлятор настраивает ядро Sing-box, генерирует криптографические ключи, прописывает домен и выдает клиенту ссылку или файл конфигурации.

Однако в условиях современных ограничений Рунета парадигма Single-Node становится **точкой критического отказа (Single Point of Failure, SPOF)**:
1. **Блокировка IP-адреса или подсети провайдера:** Если ТСПУ (Технические средства противодействия угрозам) блокирует IP-адрес сервера по признаку нехарактерного зарубежного трафика, протокола или жалобе, все подключенные клиенты одномоментно теряют связь.
2. **Географическая ограниченность:** Размещение единственного сервера в Нидерландах или Германии дает отличную скорость к европейским ресурсам, но приводит к повышенному RTT (80–120 мс) до азиатских или турецких площадок, а также отсекает доступ к сервисам, жестко ограниченным регионом (банки Казахстана, локальные стриминговые платформы, сервисы OpenAI, требующие чистых не-RU IP).
3. **Отсутствие эластичности и резервирования:** Любые регламентные работы хостера, аварии в дата-центре (DDoS-атаки, обрывы магистральных оптоволоконных кабелей) полностью парализуют инфраструктуру.

**Fleet Architecture (Архитектура пула)** объединяет множество независимых узлов в единую связную сеть под централизованным или скоординированным управлением. Для конечного пользователя пул выглядит как единая подписка (Subscription URL), которая динамически предоставляет доступ к десяткам серверов с автоматическим переключением в случае деградации любого из них.

```
                     ┌────────────────────────────────────────────────────────┐
                     │          Центральный оркестратор (Master Node)         │
                     │   - users.json (реестр UUID / паролей)                 │
                     │   - fleet.json (топология, хосты, статусы, ключи)      │
                     │   - Subscription API: https://sub.example.com/sub/...  │
                     │   - Canary Monitor (контроль доступности изнутри РФ)   │
                     └───────┬──────────────────────┬──────────────────┬──────┘
                             │                      │                  │
                mTLS / SSH   │         mTLS / SSH   │       mTLS / SSH │
              Синхронизация  │        Синхронизация │    Синхронизация │
                             ▼                      ▼                  ▼
                    ┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
                    │  Node 1: NL-AMS │    │  Node 2: DE-FRA │    │  Node 3: KZ-ALA │
                    │ Sing-box + AWG  │    │ Sing-box + AWG  │    │ Sing-box + AWG  │
                    │ (Exit EU Fast)  │    │ (Exit Fallback) │    │ (Exit CIS/RU)   │
                    └─────────────────┘    └─────────────────┘    └─────────────────┘
                             ▲                      ▲                  ▲
                             │                      │                  │
                             └──────────────────────┼──────────────────┘
                                                    │
                                     Клиентский трафик (Failover / URL-Test)
                                                    │
                                           ┌─────────────────┐
                                           │ Клиент (РФ)     │
                                           │ Mihomo/Sing-box │
                                           └─────────────────┘
```

### 1.2. Вызовы цензуры в РФ: блокировки подсетей/ASN, шатдауны и трансграничные замедления

В 2024–2026 годах архитектура блокировок в РФ трансформировалась от точечной фильтрации URL и DNS к многоуровневому аппаратному DPI (ТСПУ на базе платформ «НТЦ Протей», RDP.RU и др.), установленному на узлах всех операторов связи РФ:

- **Блокировка протоколов по сигнатурам (Protocol Whitelisting/Blacklisting):** ТСПУ детектирует стандартный WireGuard, OpenVPN, Shadowsocks (старых версий) за 1–3 сетевых пакета. Решение требует протоколов с сокрытием энтропии (AmneziaWG с параметрами мусора и псевдо-заголовков) или полной маскировкой под легитимный HTTPS-трафик (VLESS Reality, Hysteria 2, TUIC v5).
- **Блокировка по IP и ASN:** Регулярные «веерные» блокировки популярных зарубежных хостингов (Hetzner, DigitalOcean, OVH, Scaleway). Узел перестает отвечать из РФ, хотя из США или Европы функционирует безупречно.
- **Трансграничное замедление (Bandwidth Throttling):** Искусственное ограничение полосы пропускания TCP/UDP на трансграничных переходах в моменты политических событий или учений по «суверенному Рунету».
- **Сценарий «Изоляция / Белые списки» (Full Border Shutdown):** Самый жесткий сценарий, при котором весь зарубежный IP-трафик блокируется по умолчанию, а связность сохраняется исключительно внутри национальной зоны `.ru` / `.рф`. Обычный зарубежный VPN в таких условиях становится полностью неработоспособен. Единственное решение — использование двухзвенной цепочки (Relay-топология) с входной точкой внутри РФ.

## 2. Архитектурные топологии пула серверов

### 2.1. Зачем нужен пул серверов: ключевые сценарии и диверсификация

#### 2.1.1. Географическая диверсификация и оптимизация задержек (Latency & RTT)

Пользователи используют VPN для совершенно разных задач, предъявляющих взаимоисключающие требования к маршрутизации:
- **Европейские ноды (Нидерланды — AMS, Германия — FRA, Финляндия — HEL):** Оптимальны для повседневного серфинга, стриминга, загрузки обновлений ПО. Обеспечивают минимальный RTT из европейской части РФ (25–45 мс) и широкую полосу пропускания (до 1–10 Гбит/с).
- **СНГ и ближнее зарубежье (Казахстан — ALA/AST):** Критически важны для пользователей с Урала, Сибири и Дальнего Востока, где RTT до Франкфурта достигает 90–140 мс, тогда как до Алматы — всего 20–35 мс. Кроме того, IP-адреса Казахстана позволяют без проблем оплачивать региональные сервисы и использовать локализованный контент.
- **Азия и Ближний Восток (Турция — IST, ОАЭ — DXB, Сингапур — SIN):** Необходимы для доступа к локальным турецким подпискам (PlayStation, Steam, Spotify), а также для пользователей, находящихся на Дальнем Востоке РФ (Владивосток/Хабаровск), для которых прямой пинг до Токио (15 мс) или Гонконга в разы быстрее, чем маршрут через Москву в Европу.
- **США (Восточное побережье — NYC, Западное — SJC):** Необходимы для доступа к американским корпоративным ресурсам, финансовым институтам и специфическим сервисам, требующим исключительно US-резидентских или чистых коммерческих IP.

#### 2.1.2. Доступность гео-зависимых сервисов (Россия vs Мир vs AI)

Современная матрица доступности ресурсов расколота на три конфликтующие зоны:
1. **Зона глобальных блокировок (Заблокировано в РФ):** Instagram, Twitter (X), Facebook, независимые СМИ, торрент-трекеры. Доступны с любого зарубежного узла пула.
2. **Зона антироссийских санкций (Заблокировано зарубежными платформами для IP из РФ):** ChatGPT (OpenAI), Claude (Anthropic), Midjourney, Spotify, Netflix. Часто блокируют не только российские IP, но и адреса некоторых подозрительных СНГ-хостингов. Требуют чистых европейских или американских нод.
3. **Зона внутренней изоляции (Заблокировано из-за рубежа российскими сервисами):** Портал Госуслуг, Федеральная налоговая служба (ФНС), Сбербанк, Т-Банк, сайты судов, локальные городские порталы блокируют или замедляют любые подключения из-за пределов Российской Федерации.
   * *Решение:* Пул должен содержать либо внутрироссийскую ноду (RU In-Country Node), либо клиентское ядро должно использовать маршрутизацию split-tunneling (через geoip/geosite), пропуская `.ru` напрямую (Direct) или заворачивая через RU-ноду.

#### 2.1.3. Юридическая диверсификация и устойчивость к бану хостинг-провайдеров

Использование одного хостинг-провайдера (например, покупка 5 серверов в Hetzner в разных локациях) не решает задачу отказоустойчивости:
- ТСПУ часто блокирует целые автономные системы (ASN) или крупные префиксы подсетей (`/18`, `/16`). Если под фильтр попадает ASN Hetzner (`AS24940`), падают все 5 серверов одновременно.
- Сам хостинг-провайдер может заблокировать аккаунт пользователя из-за санкционных ограничений, проблем с оплатой российскими или зарубежными картами, жалоб правообладателей (DMCA).
- **Правило пула `vpn-installer`:** Пул строится на базе **мульти-провайдерной модели**. Узлы должны распределяться между несвязанными независимыми хостерами (например: Node 1 — Hetzner DE, Node 2 — ServerAstra/Vultr NL, Node 3 — G-Core/PQ Hosting KZ, Node 4 — Melbicom/FlyServers).

#### 2.1.4. Выживаемость пула при блокировках IP/ASN со стороны ТСПУ

В случае точечной блокировки IP-адреса Node 1 (РФ -> Node 1 = Packet Loss 100%), архитектура пула обеспечивает непрерывность сервиса:
- Клиентское приложение по механизму `url-test` или `fallback` в течение 1–3 секунд перенаправляет трафик пользователя на Node 2 или Node 3.
- Пользователь не предпринимает никаких действий (не меняет профили, не пишет в поддержку).
- Администратор видит в мониторинге деградацию узла Node 1 и инициирует смену IP или ротацию хостинга без остановки сервиса.

### 2.2. Топология Relay (Двухуровневая цепочка / Multi-hop / Chaining)

#### 2.2.1. Архитектура: Внутрироссийский входной узел -> Зарубежный выходной узел

Топология Relay разделяет путь прохождения пакета на два сегмента:
1. **Первое плечо (First Mile: Client -> Entry Node):** Трафик от клиента из Москвы/регионов идет на сервер, физически расположенный на территории РФ (в дата-центрах Selectel, Timeweb, Cloud.ru, Beget или у региональных провайдеров).
2. **Второе плечо (Backbone / Inter-Node: Entry Node -> Exit Node):** Трафик от внутрироссийского узла направляется по высокоскоростному защищенному туннелю на зарубежный узел (в Нидерландах, Германии, Финляндии).
3. **Выход в интернет (Last Mile: Exit Node -> Target Web):** Зарубежный сервер отправляет пакет целевому ресурсу (Google, OpenAI, YouTube).

```
┌─────────────────┐       Сегмент 1: Внутри РФ       ┌──────────────────┐
│  Клиент в РФ    ├─────────────────────────────────►│  Entry Node (RU) │
│ (Mihomo/Client) │     Протокол: VLESS Reality      │  Selectel/Timeweb│
└─────────────────┘       или AmneziaWG (RU IP)      └────────┬─────────┘
                                                              │
                                                              │ Сегмент 2: Межсерверный туннель
                                                              │ (AWG / Hysteria2 / WireGuard)
                                                              │ Провайдерские каналы РФ-EU
                                                              ▼
┌─────────────────┐       Сегмент 3: Свободный Web   ┌──────────────────┐
│  Целевой сайт   │◄─────────────────────────────────┤  Exit Node (EU)  │
│ (Google/YouTube)│           Прямой TCP/UDP         │  Hetzner/Vultr   │
└─────────────────┘                                  └──────────────────┘
```

#### 2.2.2. Применение при «белых списках», изоляции Рунета и блокировке зарубежных IP

Почему эта схема критична для выживания:
- **Фильтрация на ТСПУ настроена асимметрично:** Пакеты между абонентом в РФ и зарубежными автономными системами проходят жесткий анализ, эвристический DPI и искусственное замедление. Трафик же внутри РФ (между домашним провайдером МТС/Ростелеком и дата-центром Selectel в Санкт-Петербурге) практически не подвергается трансграничным проверкам.
- **Шатдаун зарубежного сегмента (Белые списки):** Если регулятор отключает связность с зарубежными сетями для обычных пользователей, корпоративные каналы крупных российских дата-центров (Selectel, Cloud.ru) продолжают функционировать по выделенным BGP-стыкам и трансграничным оптоволоконным магистралям. Входной узел внутри РФ доступен для граждан всегда, пока работает национальный Рунет.
- **Маскировка под легитимный бизнес-трафик:** Трафик между Entry Node и Exit Node может быть инкапсулирован в корпоративный IPSec, WireGuard или замаскирован под Hysteria 2 / VLESS, сливаясь с миллионами запросов отечественных компаний к зарубежным филиалам.

#### 2.2.3. Протоколы межсерверного транспорта (Chaining Protocols)

Для связки Entry Node -> Exit Node в ядре Sing-box применяются три основных подхода:

| Протокол транспорта | Защита от цензуры | Оверхед / Производительность | Устойчивость к потерям | Рекомендация для межсерверной связки |
| :--- | :--- | :--- | :--- | :--- |
| **AmneziaWG / WireGuard Overlay** | Высокая (обфускация) | Минимальный (kernel space, ChaCha20-Poly1305) | Средняя (деградация при дропах UDP) | **Идеально** при стабильном канале между ДЦ |
| **VLESS Reality (TCP Vision)** | Максимальная (TLS 1.3) | Низкий (Zero-copy, splice) | Средняя (TCP Head-of-Line blocking) | Отлично подходит для обхода жестких проверок |
| **Hysteria 2 (QUIC / Brutal)** | Очень высокая | Средний (User-space QUIC) | **Высшая** (BBR/Brutal выжимает 100% полосы при 10–20% потерь) | **Идеально** при нестабильных трансграничных стыках |
| **Shadowsocks-2022 (AEAD)** | Средняя | Минимальный | Средняя | Подходит при отсутствии адресных блокировок |

##### Пример конфигурации Relay-цепочки в Sing-box на Entry Node:
На входном узле входящий трафик от клиентов (например, порт 443 VLESS Reality) не выходит напрямую в интернет, а перенаправляется во внешнее соединение (Outbound), указывающее на Exit Node.

```json
{

    {
      "type": "vless",
      "tag": "vless-in-ru",
      "listen": "0.0.0.0",
      "listen_port": 443,

        { "name": "alice", "uuid": "c3b522c0-8271-4a1d-b657-36e6e30b65d8" }

        "server_name": "vk.com",
        "reality": {
          "enabled": true,
          "handshake": { "server": "vk.com", "port": 443 },
          "private_key": "ENTRY_REALITY_PRIVATE_KEY",
          "short_id": ["0123456789abcdef"]
        }
      }
    }
  ],
  "outbounds": [
    {
      "type": "hysteria2",
```

#### 2.2.4. Сквозная маршрутизация и трансляция адресов (NAT, Proxy Protocol v2, MTU)

При построении двухуровневых цепочек возникают сетевые нюансы:
1. **Проблема прозрачности IP-адреса источника (Source IP Transparency):**
   При ретрансляции трафика Exit Node видит в качестве источника IP-адрес Entry Node. Для антифрод-систем и систем учета трафика это скрывает клиента. В Sing-box для передачи оригинального адреса клиента между нодами можно задействовать опцию `proxy_protocol` (Proxy Protocol v2) в цепочках с доверенными узлами.
2. **Фрагментация и MTU (Path MTU Discovery):**
   Двойная инкапсуляция (Клиент -> VLESS -> QUIC -> Интернет) снижает эффективный размер полезной нагрузки (Payload MTU). На Entry и Exit нодах необходимо на уровне ядра Linux включить TCP MSS Clamping в `iptables`/`nftables`:
   ```bash
   iptables -t mangle -A POSTROUTING -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
   ```
   В случае AmneziaWG в цепочке MTU туннеля устанавливается не более `1280–1360` байт для предотвращения дропа UDP-фрагментов промежуточными маршрутизаторами.

### 2.3. Сравнение моделей управления кластером

Существует две фундаментальные парадигмы организации управления парком узлов:

```
          ЦЕНТРАЛИЗОВАННЫЙ MASTER-WORKER                 ДЕЦЕНТРАЛИЗОВАННЫЙ GITOPS / STATELESS
          
              ┌──────────────────┐                             ┌───────────────────┐
              │   Master Node    │                             │  Git Репозиторий  │
              │  (API, БД, UI)   │                             │  или S3/Vault     │
              └────────┬─────────┘                             └─────────┬─────────┘
                       │ gRPC/mTLS Push                                  │ HTTPS/SSH Pull
          ┌────────────┼────────────┐                      ┌─────────────┼─────────────┐
          ▼            ▼            ▼                      ▼             ▼             ▼
   ┌───────────┐ ┌───────────┐ ┌───────────┐        ┌───────────┐ ┌───────────┐ ┌───────────┐
   │ Worker 1  │ │ Worker 2  │ │ Worker 3  │        │  Node 1   │ │  Node 2   │ │  Node 3   │
   │ Node Agent│ │ Node Agent│ │ Node Agent│        │ Sync-Cron │ │ Sync-Cron │ │ Sync-Cron │
   └───────────┘ └───────────┘ └───────────┘        └───────────┘ └───────────┘ └───────────┘
```

#### 2.3.1. Централизованный Master-Worker (Оркестратор + Edge-агенты)

Яркими примерами служат **Marzban** (с `marzban-node`) и **Hiddify-Manager**:
- **Принцип работы:** Центральный сервер (Master) хранит базу данных пользователей (PostgreSQL/SQLite), веб-панель и систему биллинга. На каждом периферийном сервере (Node) запускается легковесный демон-агент (`marzban-node`), написанный на Python/Go. Связь между Master и Worker осуществляется по постоянному двунаправленному **gRPC-каналу с mutual TLS (mTLS)**.
- **Преимущества:**
  - *Мгновенная реакция:* Добавление, блокировка или удаление пользователя на Master передается на все ноды за доли секунды.
  - *Централизованный сбор статистики:* Worker в потоковом режиме шлет на Master количество переданных байт по каждому пользователю.
  - *Единая точка управления:* Вся конфигурация правится в одном месте.
- **Недостатки:**
  - *SPOF мастер-узла:* Падение или блокировка Master не останавливает текущую прокси-работу Worker, но замораживает выдачу подписок, обновление списков пользователей и ротацию ключей.
  - *Сложность развертывания:* Требуется генерация и дистрибуция пар сертификатов mTLS (CA, Master cert, Node certs).

#### 2.3.2. Децентрализованный GitOps / Stateless-Worker (Pull-модель)

- **Принцип работы:** Каждый узел кластера является автономным. Данные о пользователях (`users.json`) и инфраструктуре хранятся в защищенном приватном Git-репозитории, защищенном S3-бакете или на защищенном мастер-хосте с доступом по SSH/HTTPS. На каждой ноде по таймеру `systemd` (или через локальный демон) раз в 1–5 минут отрабатывает скрипт синхронизации (`vpn-sync.sh`), который:
  1. Выкачивает актуальный `users.json`.
  2. Сравнивает хэш `sha256sum`.
  3. Если хэш изменился — компилирует боевой `config.json`, проверяет его (`sing-box check`) и выполняет атомарный `systemctl reload sing-box`.
- **Преимущества:**
  - *Максимальная живучесть:* Никакая нода не зависит от постоянного онлайн-соединения с оркестратором. Узлы работают полностью автономно.
  - *Простота и прозрачность:* Нет тяжелых демонов, оркестрация осуществляется нативными скриптами ОС.
  - *Аудит и откат:* Вся история изменений пользователей и нод сохраняется в истории коммитов Git.
- **Недостатки:**
  - *Задержка применения (Eventual Consistency):* Изменения вступают в силу с лагом до нескольких минут.
  - *Трудность сбора realtime-метрик:* Учет трафика требует отдельного контура (например, Prometheus Node Exporter + Federation).

#### 2.3.3. Сравнительная матрица моделей управления

| Параметр | Master-Worker (gRPC Push) | Stateless GitOps / S3 (Pull) | Hybrid Push-via-SSH (`vpn-installer`) |
| :--- | :--- | :--- | :--- |
| **Сложность внедрения** | Высокая (демоны, mTLS) | Средняя (Git-агенты, ключи) | **Низкая** (стандартный SSH/SCP) |
| **Скорость применения изменений** | < 1 сек | 1–5 минут | **2–5 сек** (параллельный push) |
| **Устойчивость к падению мастера** | Высокая (ноды продолжают жить) | Абсолютная (ноды автономны) | **Абсолютная** (ноды автономны) |
| **Требования к ресурсам ноды** | +30–60 МБ RAM на агент | Минимальные (cron/curl/bash) | **Нулевые** (чистый sing-box + awg) |
| **Безопасность периметра** | Нода слушает порт gRPC | Нода не открывает портов наружу | Нода открывает только порт SSH (key-auth) |

> [!TIP]
> **Выбор для архитектуры `vpn-installer`:**
> Оптимальной признана **гибридная модель (Hybrid Push-via-SSH / Fast Sync)**:
> 1. Нода остается абсолютно чистой (Stateless Worker): на ней работают только системные сервисы `sing-box` и `amnezia-wg`, без сторонних агентов.
> 2. Мастер-сервер (где администратор вызывает `vpn user add` или `vpn node add`) инициирует параллельную трансляцию `users.json` на все ноды через SSH-соединения с аутентификацией по Ed25519-ключам.
> 3. На случай временной недоступности ноды по SSH, на ноде настраивается локальный `systemd.timer`, который раз в час выполняет аварийный pull-запрос к защищенному эндпоинту мастера.

## 3. Синхронизация пользователей и ключей между несколькими нодами

### 3.1. Использование единого UUID и ключей для пользователя во всем пуле

#### 3.1.1. Почему это безопасно и удобно для клиента

В классических решениях (например, в ряде самописных панелей) для каждого нового сервера пользователю создают отдельный конфиг с новым UUID. Это приводит к хаосу: в приложении пользователя накапливается 10 профилей с невнятными названиями, ключи теряются, а ротация становится кошмаром.

В архитектуре правильного пула пользователю выдается **ровно один комплект учетных данных (Single Identity Principle)**:
- **Единый UUID:** `c3b522c0-8271-4a1d-b657-36e6e30b65d8`
- **Единый пароль Hysteria 2 / TUIC:** `SecretPass_7482`
- **Единый пароль Shadowsocks-2022 (User Key):** `QWxpY2VTU1VzZXJLZXkxNkJ5dGVzPT0=`

**Безопасность распределенного UUID:**
1. **Криптографическая коллизия невозможна:** Пространство идентификаторов UUIDv4 составляет $2^{122}$ комбинаций.
2. **Изоляция протоколов:** Знание пользователем своего UUID для подключения к VLESS Reality не дает ему возможности перехватывать чужой трафик, поскольку расшифровка TLS сессии происходит на общем эфемерном ключе сессии (ECDHE x25519).
3. **Отсутствие кросс-компрометации:** Если одна нода пула захвачена злоумышленником, он получает список UUID пользователей этой ноды, но **не получает** приватных ключей трафика других нод и не может дешифровать трафик пользователей на других серверах.

#### 3.1.2. Разделение серверных криптографических параметров и клиентских реквизитов

Архитектура строго разделяет параметры на две независимые категории:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   КАТЕГОРИИ КРИПТОГРАФИЧЕСКИХ ДАННЫХ                   │
├───────────────────────────────────┬────────────────────────────────────┤
│ СЕРВЕРНЫЕ ПАРАМЕТРЫ (Local/Node)  │ КЛИЕНТСКИЕ РЕКВИЗИТЫ (Global/Fleet)│
├───────────────────────────────────┼────────────────────────────────────┤
│ • VLESS Reality Private/Public Key│ • User UUID (VLESS, TUIC)          │
│ • Reality Short IDs (per node)    │ • User Password (Hysteria 2, TUIC) │
│ • TLS Certificates (Hysteria2)    │ • User Sub-Key (Shadowsocks-2022)  │
│ • External IP / Inbound Ports     │ • AmneziaWG Client IP / Private Key│
│ • SNI Target (Decoy Domain)       │ • Срок действия (expires_at)       │
└───────────────────────────────────┴────────────────────────────────────┘
```

Серверные параметры формируются индивидуально при установке каждой ноды и сохраняются в `/etc/vpn-installer/manifest.json`. Клиентские реквизиты генерируются централизованно один раз и реплицируются в `/etc/vpn-installer/users.json` на все ноды кластера.

#### 3.1.3. Сквозная аутентификация в мультипротокольной среде

Каждая нода кластера запускает идентичный набор Inbounds в Sing-box. При компиляции конфигурации из `users.json` один и тот же массив пользователей транслируется во все протоколы:

### 3.2. Специфика AmneziaWG в мультисерверном пуле

В отличие от Sing-box, который работает на прикладном уровне (L7 / L4 Proxy), протокол **AmneziaWG (AWG)** функционирует на сетевом уровне ядра (L3 VPN, интерфейс `awg0`). Это накладывает строгие требования на распределение IP-адресов.

#### 3.2.1. Выделение IP-адресов в туннельной подсети (IPAM)

В кластере из нескольких серверов AWG существует две модели адресации:

```
ВАРИАНТ A: НЕЗАВИСИМЫЕ ПОДСЕТИ (РЕКОМЕНДУЕМЫЙ)  ВАРИАНТ B: ОБЩАЯ ПОДСЕТЬ + ОВЕРЛЕЙ
┌──────────────────┐  ┌──────────────────┐     ┌──────────────────┐  ┌──────────────────┐
│  Node 1: NL      │  │  Node 2: DE      │     │  Node 1: NL      │  │  Node 2: DE      │
│  awg0:           │  │  awg0:           │     │  awg0:           │  │  awg0:           │
│  10.8.1.1/24     │  │  10.8.2.1/24     │     │  10.8.0.1/16     │  │  10.8.0.2/16     │
└────────┬─────────┘  └────────┬─────────┘     └────────┬─────────┘  └────────┬─────────┘
         │                     │                        │                     │
   Клиент Alice:         Клиент Alice:                  └──────────┬──────────┘
   10.8.1.2              10.8.2.2                           Клиент Alice: 10.8.10.5
                                                            (Требует BGP/OSPF маршрутизации)
```

1. **Модель независимых подсетей (Independent Subnet Allocation):**
   Каждому серверу пула выделяется своя фиксированная туннельная подсеть `/24`:
   - `Node 1 (NL)`: шлюз `10.8.1.1/24`, диапазон клиентов `10.8.1.2` – `10.8.1.254`
   - `Node 2 (DE)`: шлюз `10.8.2.1/24`, диапазон клиентов `10.8.2.2` – `10.8.2.254`
   - `Node 3 (KZ)`: шлюз `10.8.3.1/24`, диапазон клиентов `10.8.3.2` – `10.8.3.254`
   - `Node 4 (RU)`: шлюз `10.8.4.1/24`, диапазон клиентов `10.8.4.2` – `10.8.4.254`
   
   Пользователь `alice` получает детерминированный IP-смещение внутри подсети (например, индекс 2):
   - При подключении к NL её туннельный IP: `10.8.1.2`
   - При подключении к DE её туннельный IP: `10.8.2.2`

2. **Преимущества независимых подсетей:**
   - Полная автономия узлов: падение одной ноды не нарушает сетевые таблицы маршрутизации других серверов.
   - Отсутствие необходимости настраивать сложные динамические протоколы маршрутизации (BGP/OSPF mesh) между нодами.
   - Корректная работа NAT (`iptables -t nat -A POSTROUTING -s 10.8.X.0/24 -o eth0 -j MASQUERADE`).

#### 3.2.2. Коллизии IP-адресов при одновременном подключении и роуминге

Если бы клиент использовал один и тот же статический IP `10.8.0.2` на всех серверах, то при одновременном подключении двух устройств (например, iPhone к NL, а ноутбук к DE под одним профилем) и наличии межсерверного туннеля возник бы конфликт адресов (IP duplicate conflict). 

Использование схемы **`10.8.<Node_ID>.<User_ID>`** гарантирует 100% защиту от коллизий.

#### 3.2.3. Ротация obfuscation-параметров (`Jc`, `Jmin`, `Jmax`, `S1`, `S2`, `H1`-`H4`) в пуле

AmneziaWG защищает трафик от DPI за счет добавления случайного «мусора» (Junk Packet) в начало рукопожатия и модификации стандартных заголовков WireGuard:
- `Jc`: Количество мусорных пакетов (1–5).
- `Jmin`, `Jmax`: Минимальный и максимальный размер мусора (например, `40` и `70` байт).
- `S1`, `S2`: Смещение размера пакетов инициации и ответа.
- `H1`, `H2`, `H3`, `H4`: Кастомные 4-байтовые идентификаторы типов пакетов (вместо стандартных WG 1, 2, 3, 4).

> [!IMPORTANT]
> **Правило консистентности AWG для пула:**
> Все серверы пула **могут** иметь как идентичные, так и индивидуальные параметры обфускации. Однако для упрощения клиентской конфигурации рекомендуется генерировать **единый набор параметров обфускации (Cluster Obfuscation Profile)** для всего кластера, либо включать их индивидуально в секции каждого сервера в конфигурационном файле.

## 4. Клиентская подсистема и автоматический Failover (Client-Side Pool Handling)

### 4.1. Централизованный сервис подписок (Subscription Delivery API)

#### 4.1.1. Архитектура Subscription URL

Единая точка входа для всех клиентских приложений — защищенный HTTP-эндпоинт:
```
https://sub.pool-domain.com/sub/<secure_token>
```
Например:
`https://sub.example.com/sub/dGhpcy1pcy1hLXNlY3VyZS0yNTYtYml0LXRva2Vu`

Сервис доставки подписок выполняет три задачи:
1. **Аутентификация:** Проверяет валидность токена пользователя в единой базе `users.json`, проверяет статус (`active` vs `suspended`) и срок действия (`expires_at`).
2. **Фильтрация нод (Live Fleet State):** Исключает из конфигурации ноды, помеченные системой мониторинга как упавшие или заблокированные на ТСПУ внутри РФ.
3. **Контентная адаптация:** На основе заголовка `User-Agent` определяет клиентское приложение и отдает конфигурацию в требуемом формате.

```
Клиентский запрос: GET /sub/<token>
  │
  ├─ User-Agent: "clash.meta" / "Mihomo" ──► Отдает: YAML (Proxy Providers + Groups)
  ├─ User-Agent: "sing-box" / "SFI" / "SFM" ─► Отдает: JSON (Outbounds: urltest + selector)
  ├─ User-Agent: "AmneziaVPN" ──────────────► Отдает: JSON (Amnezia multi-server backup)
  └─ User-Agent: "v2rayN" / "FoXray" / curl ─► Отдает: Base64 URI List (vless://, hy2://)
```

#### 4.1.2. Криптографическая безопасность токенов, защита от сканирования и ротация

- **Формат токена:** Случайная 32-байтовая криптографическая последовательность в кодировке Base64URL (256 бит энтропии). Угадать или перебрать такой токен методом brute-force математически невозможно.
- **Защита от сканирования DPI и ботов (Anti-Crawl):**
  - При обращении к корню `https://sub.domain.com/` или несуществующему токену сервер отдает фиктивный ответ `404 Not Found` (или редирект на Wikipedia / Яндекс), не раскрывая назначение сервиса.
  - Ограничение частоты запросов (Rate Limiting): Не более 10 запросов в минуту с одного IP-адреса через Nginx `limit_req_zone`.
- **Ротация токенов:** При компрометации подписки пользователь может сменить токен одной командой в CLI (`vpn user rotate-token alice`).

### 4.2. Конфигурация Clash.Meta / Mihomo (YAML)

Ядро **Mihomo** (ранее Clash.Meta) — наиболее мощный и распространенный кроссплатформенный клиент обхода блокировок. Он обладает встроенными механизмами тестирования доступности и интеллектуальной маршрутизации.

#### 4.2.1. Группа `type: url-test` (Автоматический выбор наименьшей задержки)

Группа периодически отправляет HTTP-запрос `GET /generate_204` через каждый прокси-сервер пула, измеряет RTT и переключает маршрут на самый быстрый живой узел:
- `url: https://cp.cloudflare.com/generate_204` (или `http://www.gstatic.com/generate_204`).
- `interval: 300`: Период тестирования каждые 300 секунд (5 минут).
- `tolerance: 50`: Порог переключения (мс). Если текущий сервер имеет пинг 60 мс, а соседний 55 мс, переключение не происходит (предотвращает flapping соединений).
- `lazy: true`: Тестирование выполняется только тогда, когда группа реально используется активным трафиком.

#### 4.2.2. Группа `type: fallback` (Отказоустойчивое переключение по приоритету)

Работает по строгому приоритету сверху вниз:
- Трафик всегда направляется на первый сервер списка (`Node 1 (NL)`).
- Если `Node 1` перестает отвечать на проверки доступности (HTTP 204 не получен), трафик мгновенно переключается на `Node 2 (DE)`.
- Как только `Node 1` восстанавливается, соединение автоматически возвращается на приоритетный сервер.

#### 4.2.3. Группа `type: load-balance` (Балансировка нагрузки)

- `strategy: consistent-hashing`: Все запросы к одному целевому хосту (например, `*.youtube.com`) идут через один и тот же выходной сервер (критично для веб-сайтов с авторизацией по сессионным cookie).
- `strategy: round-robin`: Циклическое распределение новых TCP-сессий между серверами пула (максимизирует суммарную пропускную способность).

#### 4.2.4. Группа `type: select` (Ручной выбор)

Позволяет пользователю в интерфейсе приложения вручную выбрать желаемый узел: конкретную страну, авто-выбор по скорости или цепочку Relay.

## 5. Мониторинг здоровья нод и детекция блокировок из РФ

### 5.1. Разница между системным падением и блокировкой ТСПУ

Традиционные системы мониторинга (Zabbix, Uptime Kuma, Datadog), запущенные на зарубежных серверах, категорически **непригодны** для VPN-пулов, ориентированных на пользователей из РФ:

```
                               ┌────────────────────────────────────────────────────────┐
                               │           МАТРИЦА ДЕТЕКЦИИ СОСТОЯНИЯ УЗЛА              │
┌──────────────────────────────┼───────────────────────────┬────────────────────────────┤
│ Симптом                      │ Внешний мониторинг (EU/US)│ Зонд изнутри РФ (Canary RU)│
├──────────────────────────────┼───────────────────────────┼────────────────────────────┤
│ 1. Сервер выключен (OOM/Хост)│ ❌ Down (ICMP/TCP fail)   │ ❌ Down                    │
│ 2. Блокировка IP ТСПУ        │ ✅ UP (Пинг 5 мс, HTTP OK)│ ❌ Down (Timeout / RST)    │
│ 3. Блокировка TLS SNI ТСПУ   │ ✅ UP (Все проверки OK)   │ ❌ Down (TLS Handshake fail│
│ 4. Блокировка UDP (Hysteria) │ ✅ UP (TCP/HTTP OK)       │ ❌ Down (UDP 100% loss)    │
│ 5. Замедление до 128 кбит/с  │ ✅ UP (1 Гбит/с)          │ ⚠️ Degraded (RTT > 1500ms) │
└──────────────────────────────┴───────────────────────────┴────────────────────────────┘
```

#### 5.1.1. Механика блокировок ТСПУ
- **RST Injection:** На этапе отправки TLS ClientHello ТСПУ со стороны оператора отправляет клиенту поддельный TCP RST пакет, немедленно разрывая сессию, в то время как зарубежный сервер даже не получил пакет.
- **Silent Drop / Blackhole:** Пакеты UDP или TCP SYN просто сбрасываются пограничным DPI-маршрутизатором. Клиент ожидает ответа вплоть до истечения таймаута (15–30 секунд).
- **TLS Handshake Hang:** TCP-соединение успешно открывается (SYN-ACK), но как только пересылается ClientHello с определенным SNI или незамаскированным протоколом, канал «замораживается».

---

### 5.2. Методология синтетических проверок изнутри РФ

Чтобы сервис подписок обладал достоверной информацией, система мониторинга должна использовать **Canary Probe (Контрольный агент внутри РФ)**:

```
┌─────────────────────────────────────────────────────────────────────────┐
│              АРХИТЕКТУРА СИНТЕТИЧЕСКОГО МОНИТОРИНГА ИЗ РФ               │
│                                                                         │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │               Canary Probe Node (Selectel / МТС, РФ)            │   │
│   │                                                                 │   │
│   │   Скрипт vpn-canary-checker:                                    │   │
│   │   1. Синтетическое рукопожатие VLESS Reality (через sing-box)   │   │
│   │   2. Синтетическое рукопожатие Hysteria 2 (QUIC Handshake)      │   │
│   │   3. AmneziaWG Handshake (Проверка получения response-пакета)   │   │
│   │   4. Замер времени до первого байта (TTFB) через https://...   │   │
│   └────────────────────────────────┬────────────────────────────────┘   │
│                                    │ JSON Health Report                 │
│                                    │ POST https://master/api/node-health│
│                                    ▼                                    │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │             Master Node: Fleet Health Controller                │   │
│   │                                                                 │   │
│   │   - Обновление статусов в fleet.json                            │   │
│   │   - Исключение заблокированной ноды из Subscription API         │   │
│   │   - Отправка алерта администратору (Telegram Bot)               │   │
│   └─────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 5.2.1. Синтетические рукопожатия (Active Protocol Probing)

Простая проверка `curl -I https://ip:port` не работает для VLESS Reality, так как порт не отвечает на стандартные HTTP/HTTPS запросы (срабатывает fallthrough маскировка под чужой сайт).

Правильная проверка реализуется путем запуска **микро-клиента Sing-box** на Canary-узле:
1. Canary-узел поднимает временный изолированный инстанс `sing-box` с конфигурацией клиента к тестируемой ноде.
2. Делает тестовый запрос к эталонному ресурсу через созданный туннель:
   ```bash
   curl -s -x socks5h://127.0.0.1:10800 --max-time 5 https://cp.cloudflare.com/generate_204
   ```
3. Если HTTP-код 204 получен быстрее чем за 3.0 секунды — нода помечается как `healthy_ru: true`.
4. Если получен таймаут или отказ соединения — нода помечается как `blocked_in_ru: true`.

### 5.3. Динамическая фильтрация и исключение сбойных нод

#### 5.3.1. Алгоритм фильтрации и гистерезис (Anti-Flapping)

Чтобы избежать постоянного «мигания» серверов в подписке из-за единичных потерь пакетов, применяется алгоритм гистерезиса:
- **Перевод в статус UNHEALTHY / BLOCKED:** Требуется **3 подряд** неудачные проверки с интервалом в 30 секунд (в течение 90 секунд).
- **Возврат в статус HEALTHY:** Требуется **5 подряд** успешных проверок (в течение 150 секунд).
- **Период охлаждения (Cooldown Period):** После восстановления нода удерживается на карантине в течение 10 минут перед добавлением в группы автовыбора.

```
       Успешные проверки
    ───────────────────────►
[ HEALTHY ]             [ PROBATION / COOLDOWN ]
    ▲                       ▲
    │                       │ 5 успешных проверок подряд
    │ 10 мин без сбоев      │
    │                       │
[ RECOVERING ]          [ BLOCKED / UNHEALTHY ]
    ▲                       │
    └───────────────────────┴── 3 неудачные проверки подряд
```

#### 5.3.2. Мгновенная инвалидация кэша подписок при блокировке

При фиксации блокировки ноды оркестратор:
1. Выставляет флаг `"is_available_ru": false` в `fleet.json`.
2. Очищает Fast-кэш Subscription API (Redis / In-memory TTL).
3. При следующем запросе клиента `GET /sub/<token>` скомпрометированный сервер исключается из отдаваемого списка `proxies` и групп `url-test`.
4. Клиент автоматически переключается на оставшиеся рабочие ноды.

## 6. Проектирование системы управления пулом для `vpn-installer`

### 6.1. Архитектура ролей: Master / Orchestrator и Worker / Node

Для проекта `vpn-installer` проектируется двухуровневая модель:

1. **Роль Master (Оркестратор):**
   - Разворачивается на основном (или защищенном) сервере кластера.
   - Содержит CLI-утилиту `vpn` с расширенными командами `vpn node` и `vpn user`.
   - Хранит глобальные реестры:
     - `/etc/vpn-installer/users.json` (пользователи).
     - `/etc/vpn-installer/fleet.json` (ноды пула).
   - Запускает сервис выдачи подписок `vpn-sub.service`.
   - Имеет SSH-ключ Ed25519 для беспарольного администрирования всех Worker-нод.

2. **Роль Worker (Нода кластера):**
   - Легковесный сервер с минимальной инсталляцией ОС (Debian 12 / Ubuntu 24.04).
   - Работают только:
     - `sing-box.service` (ядро прокси).
     - `amnezia-wg.service` (ядро AWG).
     - `sshd.service` (доступ только по SSH-ключу мастера).
   - Не требует баз данных, Docker, Python или веб-серверов.

### 6.3. Протокол межсерверной синхронизации (Sync Engine)

Синхронизация состояния выполняется по транзакционному протоколу Push-over-SSH:

```
  Администратор вызывает: vpn user add alice
                    │
                    ▼
   [ 1. Локальная модификация на Master ]
   - Обновление users.json
   - Генерация локального config.json
   - Валидация: sing-box check
   - Reload локального sing-box (SIGHUP)
                    │
                    ▼
   [ 2. Параллельная репликация на Worker ноды ]
   Для каждой ноды из fleet.json параллельно (background tasks):
   ┌─────────────────────────────────────────────────────────────┐
   │ a. scp /etc/vpn-installer/users.json worker:/tmp/users.new  │
   │ b. ssh worker "vpn-apply-users /tmp/users.new"              │
   │    └─► скрипт vpn-apply-users:                              │
   │        - компиляция боевого /etc/sing-box/config.json       │
   │        - верификация: sing-box check                        │
   │        - атомарный mv /tmp/users.new /etc/.../users.json    │
   │        - systemctl reload sing-box                          │
   │ c. Обработка exit-кода: если 0 -> OK, если != 0 -> Alert    │
   └─────────────────────────────────────────────────────────────┘
                    │
                    ▼
   [ 3. Инвалидация кэша подписок ]
   - Очистка Subscription API Cache
   - Пользователь alice мгновенно получает доступ во всем пуле
```

### 6.4. Спецификация CLI-интерфейса `vpn node`

Расширение CLI `vpn-installer` для управления пулом:

| Команда | Описание |
| :--- | :--- |
| `vpn node add <ip> [flags]` | Подключение нового сервера в пул. Автоматически выполняет bootstrap: установку Sing-box/AWG, генерацию ключей, настройку firewall и регистрацию в `fleet.json`. |
| `vpn node list` | Вывод форматированной таблицы состояния всех нод пула: статус, геолокация, RTT из РФ, количество активных соединений, протоколы. |
| `vpn node check [name]` | Принудительный запуск синтетического теста доступности ноды (или всех нод) через российский Canary Probe. |
| `vpn node remove <name>` | Исключение ноды из пула: удаление из подписок, деактивация демонов на удаленном сервере. |
| `vpn node sync` | Принудительная синхронизация базы пользователей `users.json` со всеми нодами кластера. |
| `vpn node relay-link <entry> <exit>` | Настройка связки Relay (проброс трафика от Entry-ноды к Exit-ноде). |

## 7. Эталонные реализации компонентов

### 7.1. Микросервис генерации подписок и API пула

Ниже приведен легковесный, готовый к эксплуатации сервис доставки подписок, написанный на Python с использованием асинхронного фреймворка FastAPI:

```python
#!/usr/bin/env python3
"""
vpn-sub-service: Высокопроизводительный асинхронный сервис доставки подписок
для кластера vpn-installer.
"""

import json
import os
import base64
from typing import Dict, Any, List
from fastapi import FastAPI, HTTPException, Header, Response
import yaml

USERS_DB_PATH = "/etc/vpn-installer/users.json"
FLEET_DB_PATH = "/etc/vpn-installer/fleet.json"

app = FastAPI(title="VPN Fleet Subscription Delivery API", docs_url=None, redoc_url=None)

def load_json(path: str) -> Dict[str, Any]:
    if not os.path.exists(path):
        return {}
    with open(path, "r", encoding="utf-8") as f:
        return json.load(f)

def get_user_by_token(token: str) -> Dict[str, Any]:
    users_data = load_json(USERS_DB_PATH)
    for u in users_data.get("users", []):
        # Токеном подписки может выступать id или специальный sub_token
        if u.get("sub_token") == token or u.get("id") == token:
            if u.get("status") == "active":
                return u
    return None

def get_healthy_nodes() -> List[Dict[str, Any]]:
    fleet_data = load_json(FLEET_DB_PATH)
    healthy = []
    for node in fleet_data.get("nodes", []):
        # Исключаем ноды, заблокированные в РФ или имеющие статус offline
        health = node.get("health", {})
        if health.get("status") == "healthy" and not health.get("blocked_in_ru", False):
            healthy.append(node)
    return healthy

@app.get("/sub/{token}")
async def get_subscription(token: str, user_agent: str = Header(default="")):
    user = get_user_by_token(token)
    if not user:
        raise HTTPException(status_code=404, detail="Subscription not found")

    nodes = get_healthy_nodes()
    if not nodes:
        raise HTTPException(status_code=503, detail="No healthy nodes available")

    ua = user_agent.lower()

    # 1. Запрос от Clash.Meta / Mihomo
    if "clash" in ua or "mihomo" in ua or "stash" in ua:
        content = generate_clash_yaml(user, nodes)
        return Response(content=content, media_type="application/x-yaml")

    # 2. Запрос от Sing-box (SFI, SFM, Sing-box core)
    elif "sing-box" in ua or "sfi" in ua:
        content = generate_singbox_json(user, nodes)
        return Response(content=json.dumps(content, indent=2), media_type="application/json")

    # 3. Универсальный Base64 URI List (v2rayN, FoXray, Streisand)
    else:
        content = generate_base64_uri_list(user, nodes)
        return Response(content=content, media_type="text/plain; charset=utf-8")

def generate_base64_uri_list(user: Dict[str, Any], nodes: List[Dict[str, Any]]) -> str:
    lines = []
    uuid = user["credentials"]["uuid"]
    password = user["credentials"].get("password", "")

    for node in nodes:
        name = f"{node['country']} - {node['name']}"
        host = node["public_endpoints"]["domain"]

        # VLESS Reality
        if node["protocols"].get("vless_reality", {}).get("enabled"):
            vless = node["protocols"]["vless_reality"]
            uri = (f"vless://{uuid}@{host}:{vless['port']}?encryption=none"
                   f"&flow=xtls-rprx-vision&security=reality&sni={vless['sni']}"
                   f"&fp=chrome&pbk={vless['public_key']}&sid={vless['short_id']}"
                   f"&type=tcp#{name} (Reality)")
            lines.append(uri)

        # Hysteria 2
        if node["protocols"].get("hysteria2", {}).get("enabled"):
            hy2 = node["protocols"]["hysteria2"]
            uri = f"hysteria2://{password}@{host}:{hy2['port']}/?sni={hy2['domain']}#{name} (Hy2)"
            lines.append(uri)

    raw_text = "\n".join(lines)
    return base64.b64encode(raw_text.encode("utf-8")).decode("utf-8")

def generate_clash_yaml(user: Dict[str, Any], nodes: List[Dict[str, Any]]) -> str:
    uuid = user["credentials"]["uuid"]
    proxies = []
    proxy_names = []

    for node in nodes:
        node_name = f"{node['country']} - {node['name']}"
        host = node["public_endpoints"]["domain"]

        if node["protocols"].get("vless_reality", {}).get("enabled"):
            vless = node["protocols"]["vless_reality"]
            p_name = f"{node_name} [Reality]"
            proxies.append({
                "name": p_name,
                "type": "vless",
                "server": host,
                "port": vless["port"],
                "uuid": uuid,
                "network": "tcp",
                "tls": True,
                "udp": True,
                "flow": "xtls-rprx-vision",
                "servername": vless["sni"],
                "reality-opts": {
                    "public-key": vless["public_key"],
                    "short-id": vless["short_id"]
                },
                "client-fingerprint": "chrome"
            })
            proxy_names.append(p_name)

    clash_doc = {
        "port": 7890,
        "mode": "rule",
        "proxies": proxies,
        "proxy-groups": [
            {
                "name": "🚀 Fleet VPN",
                "type": "select",
                "proxies": ["⚡ Auto URL-Test", "🛡️ Fallback"] + proxy_names + ["DIRECT"]
            },
            {
                "name": "⚡ Auto URL-Test",
                "type": "url-test",
                "url": "https://cp.cloudflare.com/generate_204",
                "interval": 300,
                "tolerance": 50,
                "proxies": proxy_names
            },
            {
                "name": "🛡️ Fallback",
                "type": "fallback",
                "url": "https://cp.cloudflare.com/generate_204",
                "interval": 60,
                "proxies": proxy_names
            }
        ],
        "rules": [
            "GEOIP,RU,DIRECT",
            "MATCH,🚀 Fleet VPN"
        ]
    }
    return yaml.dump(clash_doc, allow_unicode=True, sort_keys=False)

def generate_singbox_json(user: Dict[str, Any], nodes: List[Dict[str, Any]]) -> Dict[str, Any]:
    # Упрощенная генерация Sing-box структуры
    # (полная структура аналогична разделу 4.3)
    return {"status": "ok", "user": user["name"], "nodes_count": len(nodes)}
```

### 7.2. Демон синтетического мониторинга изнутри РФ (Canary Probe)

Bash-демон, работающий на внутрироссийском сервере (Selectel/Timeweb) и выполняющий регулярную проверку доступности всех узлов пула:

```bash
#!/usr/bin/env bash
# ==============================================================================
# vpn-canary-checker: Мониторинг доступности зарубежных нод изнутри РФ
# ==============================================================================
set -euo pipefail

MASTER_API="https://master.vpn-pool.com/api/internal/health-report"
AUTH_TOKEN="CANARY_SECRET_TOKEN_998877"
CHECK_TIMEOUT=4
TEST_URL="https://cp.cloudflare.com/generate_204"

# Временный сокс-порт для локальных проверок через sing-box
TMP_SOCKS_PORT=19999

check_node_vless_reality() {
    local host="$1"
    local port="$2"
    local uuid="$3"
    local sni="$4"
    local pbk="$5"
    local sid="$6"

    # Формируем минимальный json-конфиг для одного теста
    local tmp_cfg
    tmp_cfg=$(mktemp /tmp/sb-test-XXXXXX.json)

    cat <<EOF > "$tmp_cfg"
{
  "log": { "disabled": true },
  "inbounds": [{ "type": "socks", "listen": "127.0.0.1", "listen_port": $TMP_SOCKS_PORT }],
  "outbounds": [{
    "type": "vless",
    "server": "$host",
    "server_port": $port,
    "uuid": "$uuid",
    "flow": "xtls-rprx-vision",
    "tls": {
      "enabled": true,
      "server_name": "$sni",
      "reality": { "enabled": true, "public_key": "$pbk", "short_id": "$sid" },
      "utls": { "enabled": true, "fingerprint": "chrome" }
    }
  }]
}
EOF

    # Запускаем фоновый микро-клиент
    sing-box run -c "$tmp_cfg" &
    local sb_pid=$!

    sleep 0.5

    local status="blocked"
    local http_code=0
    local rtt=0

    # Проверяем реальное соединение через созданный прокси
    if res=$(curl -s -o /dev/null -w "%{http_code}:%{time_total}" \
             -x "socks5h://127.0.0.1:$TMP_SOCKS_PORT" \
             --max-time "$CHECK_TIMEOUT" "$TEST_URL" 2>/dev/null); then
        http_code=$(echo "$res" | cut -d: -f1)
        rtt=$(echo "$res" | cut -d: -f2)
        if [[ "$http_code" == "204" ]]; then
            status="healthy"
        fi
    fi

    # Завершаем процесс и удаляем конфиг
    kill "$sb_pid" 2>/dev/null || true
    wait "$sb_pid" 2>/dev/null || true
    rm -f "$tmp_cfg"

    echo "{\"status\": \"$status\", \"rtt\": \"$rtt\"}"
}

# Пример запуска проверки ноды
# check_node_vless_reality "nl.vpn-pool.com" 443 "c3b522c0-8271-4a1d-b657-36e6e30b65d8" "speedtest.net" "PBK..." "0123"
```

### 7.3. Реализация модуля `vpn node` для Bash-инсталлятора

Ниже приведен фрагмент реализации управления нодами для интеграции в CLI `vpn-installer`:

```bash
#!/usr/bin/env bash
# ==============================================================================
# vpn-installer: Модуль управления пулом серверов (vpn node)
# ==============================================================================

cmd_node_list() {
    local fleet_file="/etc/vpn-installer/fleet.json"
    if [[ ! -f "$fleet_file" ]]; then
        echo -e "\e[31mОшибка: Файл конфигурации флота $fleet_file не найден.\e[0m"
        return 1
    fi

    echo -e "\e[1;34m=== Пул серверов VPN-Installer (Fleet Nodes) ===\e[0m"
    printf "%-16s %-12s %-6s %-16s %-10s %-10s\n" "NODE ID" "NAME" "CC" "ENDPOINT" "STATUS" "RTT (RU)"
    echo "----------------------------------------------------------------------------"

    jq -r '.nodes[] | "\(.id)\t\(.name)\t\(.country)\t\(.public_endpoints.ipv4)\t\(.health.status)\t\(.health.latency_ru_ms // "-") ms"' "$fleet_file" | \
    while IFS=$'\t' read -r id name cc ip status rtt; do
        local color="\e[32m"
        if [[ "$status" != "healthy" ]]; then color="\e[31m"; fi
        printf "%-16s %-12s %-6s %-16s ${color}%-10s\e[0m %-10s\n" "$id" "$name" "$cc" "$ip" "$status" "$rtt"
    done
}

cmd_node_sync() {
    local fleet_file="/etc/vpn-installer/fleet.json"
    local users_file="/etc/vpn-installer/users.json"

    echo -e "\e[33mЗапуск параллельной синхронизации пользователей на все ноды пула...\e[0m"

    local node_ips
    node_ips=$(jq -r '.nodes[] | select(.role != "master") | "\(.management.ip):\(.management.ssh_port // 22)"' "$fleet_file")

    for entry in $node_ips; do
        local ip="${entry%%:*}"
        local port="${entry##*:}"

        echo -e "\e[36m-> Синхронизация с нодой $ip (порт $port)...\e[0m"
        (
            scp -P "$port" -o StrictHostKeyChecking=no -o ConnectTimeout=5 \
                "$users_file" "root@$ip:/etc/vpn-installer/users.json" && \
            ssh -p "$port" -o StrictHostKeyChecking=no -o ConnectTimeout=5 \
                "root@$ip" "vpn-rebuild-config && systemctl reload sing-box" && \
            echo -e "\e[32m[✓] Нода $ip успешно обновлена.\e[0m"
        ) || echo -e "\e[31m[✗] Ошибка синхронизации ноды $ip.\e[0m" &
    done

    wait
    echo -e "\e[32mСинхронизация пула завершена.\e[0m"
}
```

## 8. Заключение и библиография

### Заключение

Переход от одиночного сервера к распределенному пулу (Fleet Architecture) в проекте `vpn-installer`:
1. **Гарантирует катастрофоустойчивость:** Никакая одиночная блокировка IP, домена или целой автономной системы хостера не способна прервать доступ клиентов благодаря механизмам `url-test`, `fallback` и двухуровневым Relay-цепочкам.
2. **Обеспечивает комфортный UX:** Пользователь получает одну ссылку подписки и единый комплект реквизитов (UUID/Password) для доступа к десяткам серверов в любой точке мира.
3. **Оптимизирует ресурсы:** Легковесная архитектура на базе чистого Sing-box и AmneziaWG на нодах без тяжелых сторонних панелей позволяет запускать узлы даже на самых бюджетных VPS (512 МБ RAM), сохраняя высокую производительность и полный контроль через единый мастер-интерфейс.
